[FRE] Guard FinishFirstRunWithoutResumeTask on macOS

Guard FinishFirstRunWithoutResumeTask() under BUILDFLAG(IS_MAC) and
record a metric tracking whether the profile picker is open when called.

FirstRunService::FinishFirstRunWithoutResumeTask() is only called in
production on macOS: in chrome/browser/app_controller_mac.mm inside
-[AppController tryToTerminateApplication] on quit
(https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/app_controller_mac.mm;l=957)
and in CreateBrowser() when opening a new window during FRE
(https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/app_controller_mac.mm;l=252).
Because this method is only used on macOS, its declaration and
definition are guarded with #if BUILDFLAG(IS_MAC).

Promoting DCHECK(ProfilePicker::IsFirstRunOpen()) to CHECK hit crashes
in production on macOS because the picker is not always open when these
callers run. There are two main scenarios where
ProfilePicker::IsFirstRunOpen() is false while resume_task_callback_ is
still set:
* Async widget teardown: ProfilePickerView::WindowClosing()
  (https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/ui/views/profiles/profile_picker_view.cc;l=777)
  immediately clears g_profile_picker_view, making
  ProfilePicker::IsFirstRunOpen() return false. However,
  resume_task_callback_ is only run and cleared later when
  FirstRunFlowController::~FirstRunFlowController()
  (https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/ui/views/profiles/first_run_flow_controller.cc;l=904)
  runs during asynchronous Widget destruction. Quitting or opening a
  browser window while widget teardown is in flight calls
  FinishFirstRunWithoutResumeTask() with IsFirstRunOpen() == false.
* Early startup or shutdown: OpenFirstRunIfNeeded() sets
  resume_task_callback_ before ProfilePicker::Show() creates
  ProfilePickerView. If g_browser_process->IsShuttingDown() is true,
  ProfilePicker::Show() early-returns without creating ProfilePickerView
  (https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/ui/views/profiles/profile_picker_view.cc;l=172).
  In this state, resume_task_callback_ is set but no picker view exists.

In FinishFirstRunWithoutResumeTask(),
ProfilePicker.FirstRun.FinishWithoutResumeTaskPickerOpen records whether
the picker was open when called.
CHECK_CURRENTLY_ON(content::BrowserThread::UI) is also added. It is safe
to proceed without crashing because OnFirstRunHasExited(kAbandonedFlow)
runs and clears resume_task_callback_ with proceed=false, marking
first-run finished, and ProfilePicker::Hide()
(https://source.chromium.org/chromium/chromium/src/+/main:chrome/browser/ui/views/profiles/profile_picker_view.cc;l=238)
is a no-op when g_profile_picker_view is null.

Also changes: removes unnecessary virtual specifier from
FinishFirstRunWithoutResumeTask() in first_run_service.h as the method
is not overridden in any subclass.

FirstRunServiceTest.FinishFirstRunWithoutResumeTaskWhenPickerNotOpen
fails without the fix and passes with it. All FirstRunServiceTest tests
pass in unit_tests.

This change was written with AI assistance.

[ChroMenu] Allow MenuHost to focus views and share owner InputMethod

Menus are shown without activation, so the owner window keeps OS focus
and FocusManager refuses to focus views inside a MenuHost. A text field
in a menu (e.g. the app menu search box) therefore cannot take focus or
receive typed text or IME input.

Let a parented MenuHost focus its views while inactive and route their
text input through the owner window's InputMethod:
- Add Widget::CanFocusViewsWithoutActivation() (false by default) and
  make Widget::GetInputMethod() virtual. MenuHost opts in when it is not
  activatable and returns its owner's InputMethod.
- FocusManager honors the opt-in: it focuses without activating, keeps
  native focus on the owner, and clears (rather than advances) focus
  when the focused view becomes unfocusable. Widgets that do not opt in
  behave as before.
- MenuHost remembers the owner's TextInputClient when focus enters the
  menu and restores it when focus leaves. It drops its own focus when
  the owner changes focus or is destroyed, so a menu text field never
  holds the shared InputMethod after the owner moves on.

On its own this CL only affects views that request focus inside a
parented menu; MenuController starts routing keyboard focus to them in
the next CL in the chain, crrev.com/c/8614781.

[ozone/wayland] Do not export toplevels that have no role

XdgForeignWrapper::ExportSurfaceToForeign() exports the root wl_surface
of a WaylandWindow without checking that it currently has an
xdg_toplevel role. The role is created in WaylandToplevelWindow::Show()
and destroyed in WaylandToplevelWindow::Hide(), so a window that has
never been shown, or that has been hidden again, cannot be exported.

Compositors reject such a request: Mutter replies with
WL_DISPLAY_ERROR_INVALID_OBJECT ("exported surface had an invalid role")
and Hyprland with an invalid_surface error ("surface must be an
xdg_toplevel"). libwayland then closes the connection, and
WaylandEventWatcher::WlDisplayCheckForErrors() CHECK-fails, which
crashes the browser. The same is reachable through
LinuxUiDelegate::ExportWindowHandle() by an embedder that parents a
dialog to a window that is not mapped, e.g. Electron's
dialog.showMessageBox() with show: false. See
https://github.com/electron/electron/issues/55141.

Report the failure to the caller instead, which is what
LinuxUiDelegate::ExportWindowHandle() already documents: the callback
runs with an empty handle and the dialog is shown without a parent. Keep
that empty handle intact in LinuxUiDelegateWayland instead of turning it
into a "wayland:" prefix with no handle, which is not a valid window
identifier.

Add a mock zxdg_exporter_v2 to the Wayland test compositor, and unit
tests covering the visible and the non-visible cases at both the wrapper
and the LinuxUiDelegate level.

[glic] Confirm user Back/Forward during an actor task

- ActorNavigationThrottle skipped every FORWARD_BACK navigation,
  because HistoryTool and the toolbar Back button both call
  NavigationController::GoBack() and create the same navigation.

- HistoryTool now tags the history navigations it starts with
  HistoryToolNavigation, a NavigationHandleUserData set in
  DidStartNavigation, which runs before the throttle.

- HistoryTool claims a navigation only if it starts inside GoBack()
  or GoForward(), or if its navigation ID matches a returned handle.
  An unrelated history navigation, such as a user Back while the tool
  waits for an iframe, is no longer tracked or tagged.

- The throttle skips the leave confirmation for tagged navigations.
  Other browser-initiated history navigations are treated as user UI
  navigations and go through the confirmation checks, on Desktop and
  desktop Android. The is_desktop() check still excludes phones.

- The same-URL exemption no longer applies to history navigations.
  Two entries can share a URL, so going back to one moves to another
  entry instead of reloading the page.

- BFCache restores skip NavigationThrottles, so a Back to a cached
  page is still not confirmed. The follow-up CL handles it in
  ActorCommitDeferringCondition.

- Added unit tests, which also run on desktop Android, for Stay and
  Leave on an untagged Back/Forward, a same-URL history navigation,
  and phones.

- Added browser tests for user Back (Stay and Leave), HistoryTool
  Back and Forward with the confirmation enabled, a HistoryTool Back
  that starts after beforeunload, and a user Back while HistoryTool
  waits for an iframe Back.

[ProfilesReordering] Blur profile card on drag start

When initiating a drag on a profile card, the mouse down event focuses
the inner #profileCardButton, causing the <profile-card> element to
match `.profile-item:focus-within` (which applies the hover highlight
background color). Because Lit updates `.profileState` in place on the
existing <profile-card> DOM elements when reordering finishes on
dragend, the <profile-card> DOM element at the initial drag index
retains focus while displaying the newly shifted profile, leaving that
card unexpectedly highlighted after drag end.

Blur the profile card when `drag-tile-start` is dispatched so that it
does not remain focused or highlighted after the drag ends.

[Actor] Require actionable APC for frame TOCTOU

Initial Glic page context fetches can cache a default-mode
AnnotatedPageContent (ANNOTATED_PAGE_CONTENT_MODE_DEFAULT) in
ActorTabData, which omits the geometry and z-order metadata required by
FindNodeAtPoint() for coordinate hit-testing. Previously,
PageTool::ComputeObservedTargetAndValidateFrame() ran
ValidateTargetFrameCandidate() whenever any prior observation existed,
causing turn-1 coordinate actions to fail with
kFrameLocationChangedSinceObservation even when
kGlicActorToctouValidation is disabled.

Treat only ANNOTATED_PAGE_CONTENT_MODE_ACTIONABLE_ELEMENTS snapshots as
actionable observations for coordinate frame TOCTOU validation so turn-1
coordinate actions succeed when kGlicActorToctouValidation is disabled,
while preserving browser-side frame candidate validation whenever an
actionable APC is cached.
