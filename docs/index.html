[MiraclePtr] Enforce raw_ptr in templated containers in content/shell and web_test

`raw_ptr<T>` for elements stored inside templated containers (such as
`std::vector` and `std::array`). This aligns with the broader MiraclePtr
safety initiative to protect against use-after-free vulnerabilities.

This advances MiraclePtr's expansion to containers and preempts an
upcoming clang-plugin update that will strictly ban these un-rewritten
instances.

[Contextual Tasks] Clear Lens region on composebox clear

When a region selected in the Lens overlay was attached to the
Contextual Tasks composebox as an "Ask about this image" chip, clearing
the composebox removed the chip but left the region selection drawn on
the overlay. ContextualTasksComposeboxHandler::ClearFiles() reset its
visual selection tokens without notifying the overlay.

ClearFiles() now clears the overlay's region selection when a visual
selection was attached, while keeping the overlay open so the user can
select a new region. Removing the chip directly through DeleteContext()
still closes the overlay, which is intended.

LensComposeboxController now also calls ClearRegionSelection() instead
of ClearAllSelections() when its visual selection chip is removed or its
files are cleared. This clears only the region selection and its
thumbnail, matching the scope of the removed context, rather than every
selection on the overlay.

Adds an interactive UI test that opens the overlay from the Contextual
Tasks composebox Lens button, selects a region, clicks the composebox
clear button, and verifies the region selection is cleared.

[CustomTabs] Deflake CustomTabActivityEphemeralTest#testNonInteractiveOmnibox

CustomTabActivityEphemeralTest.launchCustomTabActivity() called
CustomTabActivityTestRule.startCustomTabActivityWithIntent(), which
invokes waitForFirstFrame() and polls WebContents FrameInfo with a 3000ms
timeout. None of the tests calling launchCustomTabActivity() interact
with DOM elements in WebContents (testNonInteractiveOmnibox only clicks
the Android R.id.title_url_container view in CustomTabToolbar, and
testPopupCreationBlockedAndDoesNotCrashOnClose calls
startCustomTabActivityWithIntent() directly). Under load on CI emulators,
renderer compositor FrameInfo updates can take over 3000ms after page
load, causing waitForFirstFrame() to time out.

Use startCustomTabActivityWithIntentNotWaitingForFirstFrame() in
launchCustomTabActivity(), remove the redundant waitForTabPageLoaded()
call in testNonInteractiveOmnibox(), dismiss the PageInfoController
dialog before tearDown(), and reset IncognitoReauthSettingUtils in
testIncognitoReauthPageNotShown().

AudioWorkletProcessor::Process previously scanned all 128 float elements
in ParamValueMapMatchesToParamsObject and CloneParamValueMapToObject on

regardless of automation rate or sample accuracy.

audio-thread heap allocations:

  RenderQuantumFrames() on the main thread and expose active

fontconfig: Unblock C/C++ compilation from Rust bindgen actions

Previously, `component("fontconfig")` included `:fontconfig_fontations_ffi`
directly in its `deps`. Because `:fontconfig_fontations_ffi` depends on
`rust_bindgen("fcint_h_bindgen")` and `rust_bindgen("fontconfig_h_bindgen")`,
GN propagated the bindgen action outputs into `fontconfig.harddeps`.

As a result, all fontconfig C files (such as `fcatomic.c` and `fccfg.c`) as
well as downstream C/C++ compile steps depending on `//third_party/fontconfig`
were blocked waiting for the Rust bindgen actions and Rust sysroot (`libstd`)
to complete (~68 seconds in build traces), delaying up to 5,477 compile steps.

However, fontconfig's C implementation only references the Rust symbol via
an extern declaration (`extern int add_patterns_to_fontset(...)` in
`fcfontations.c`) and does not include any generated bindings.

Split the fontconfig C compilation into a `source_set("fontconfig_sources")`
without the Rust dependency, and have `component("fontconfig")` depend on
`:fontconfig_sources` and `:fontconfig_fontations_ffi`. This removes the
bindgen action from C harddeps, allowing fontconfig C sources and downstream
C++ targets to compile immediately at the start of the build.

[PWA] Fix origin association backfill landing in the future

When an app has no origin_association_last_validation_check_time, the
command backfills one. The comment says to randomize it "in the past to
ensure no network fetch spikes", but the code computed
Now() + delta + base::Days(1), which is 1-2 days in the future.

Combined with the 24h throttle below, that defers the first real
revalidation to Now() + delta + 2 days -- 2 to 3 days out, rather than
the intended 0 to 1. A revoked scope extension therefore stays trusted
about two days longer than the throttle promises, on every launch path,
for any app whose timestamp is unset.

- base::Days(1) is what the surrounding code describes: the stored time
lands in [now - 1 day, now], and the throttle turns that into a first
fetch at a uniformly random point within 24 hours, which is what spreads
the load.

The existing test asserted the bug rather than the intent:

  // The time should be within the last 10 days.

The comment says the past; the assertion required the future. Assert both
bounds instead, so the offset cannot silently flip sign again, and add
NotThrottledWithinADayOfBackfill to cover the property that actually
matters -- that a backfilled app becomes eligible within a day. Both tests
fail against the previous arithmetic.

[CRD Linux] Terminate the logind session when desktop-session exits

pam_systemd moves the session processes started by
chrome-remote-desktop-x11-session@.service into the logind session
scope, so KillMode doesn't cover them, and cleanup() only kills
desktop-session's direct children. Daemonized processes, such as XDG
autostart apps, keep running after desktop-session exits. With the
default KillUserProcesses=no, logind then leaves the session in the
"closing" state indefinitely, and `loginctl terminate-session` becomes
a no-op.

Explicitly terminate the logind session via Session.Terminate after
cleanup(), while the session is still active, so that logind stops the
session scope. This is similar to how GDM's gnome-headless-session
terminates its sessions. SIGTERM and SIGHUP are ignored right before
the call, since terminating the session also signals desktop-session
itself, which would otherwise interrupt the atexit handlers and could
drop RELAUNCH_EXIT_CODE. The session is only terminated if its PAM
service is chrome-remote-desktop and this process is its leader, so
running the script manually from another session doesn't log the user
out. Each D-Bus call has a short timeout, so that a hung logind can't
delay the exit past TimeoutStopSec.

Also fix the misleading KillMode comment in the unit file.

ui: Decouple qr_code_generator dependency from chrome/browser/ui:ui

Previously, `static_library("ui")` in `//chrome/browser/ui` depended on
both `//components/qr_code_generator:bitmap_generator` and
`//chrome/browser/ui/views/qrcode_generator`. Furthermore,
`//chrome/browser/ui/views/qrcode_generator` exposed
`//components/qr_code_generator` in its `public_deps`.

`//third_party/rust/qr_code/v2:cpp_api_from_rust_crubit_action` to be

`//chrome/browser:core`, and `chrome_content_browser_client.cc`, blocking
up to 804 heavy C++ compilations until t = 111.23s on the critical path.

directly, and `browser_view.cc` only had dead unused includes of
`qrcode_generator_bubble_controller.h` and `qrcode_generator_bubble.h`.

Remove the unused dependencies from `//chrome/browser/ui:ui`, remove the
dead includes from `browser_view.cc`, and move `qr_code_generator` from
`public_deps` to private `deps` in `//chrome/browser/ui/views/qrcode_generator`.
This completely unblocks `//chrome/browser:core` and
`chrome_content_browser_client.cc` from waiting for Rust Crubit actions.

gpu: Zero-initialize the offscreen backbuffer in ResizeOffscreenFramebuffer

The validating decoder allocates the offscreen target color texture with
uninitialized storage and relies on a native glClear to initialize it.
On drivers with the gl_clear_broken workaround, glClear is unreliable,
and the workaround's draw-based clear (ClearFramebufferForWorkaround)
can't be used here because ResizeOffscreenFramebuffer runs from
Initialize() before clear_framebuffer_blit_ is created. Since
AllocateStorage() marks the level as fully cleared, the texture is never
lazily cleared afterwards, so its contents could be left as recycled
GPU memory.

Upload zeros when allocating the storage so the backbuffer contents are
defined regardless of glClear behavior. This is a one-time allocation
at context initialization, so the cost is negligible.

[EVP] Require a bare host name in the DNS iss= record

The spec says the DNS delegation record carries `iss=` followed by the
issuer's host name (§3.1), and that the issuer identifier is "https://"
followed by that host, with no port, path or trailing slash, compared
byte-for-byte (§3.2):
https://dickhardt.github.io/email-verification/draft-hardt-email-verification.html#name-dns-delegation
https://dickhardt.github.io/email-verification/draft-hardt-email-verification.html#name-issuer-identifier

Chromium only checked that the value was non-empty and then passed it
through GURL, which silently normalized it: a port was kept in the
issuer identifier, a path was dropped, uppercase was lowercased, and a
query, fragment or userinfo was carried into the
.well-known/email-verification URL.

Now the record is rejected with kDnsInvalidRecord unless its value is
already exactly a canonical host. Existing issuers publish bare hosts
(e.g. iss=accounts.google.com) and are unaffected.

[WebUI Toolbar] Align home button plain-text drop behavior on macOS

Aligns drag-and-drop on the WebUI toolbar home button with the native
Views HomeButton on macOS.

The native HomeButton only accepts drops that carry a URL. On macOS,
ui::clipboard_util::URLsAndTitlesFromPasteboard() already synthesizes a
URL from URL-like plain text, so such drags reach the WebUI toolbar as
`text/uri-list` and are routed to OnHomeButtonDropUrl(). A drop that is
still `text/plain` only therefore carries no URL, and the native button
ignores it regardless of where the drag started.

WebUIHomeControl::ShouldHandleDropText() now returns false on macOS for
every `text/plain`-only drop, and consumes the pending drag origin state
so it does not leak into later navigations.

a phone icon. Clicking either item opens the corresponding Send Tab to
