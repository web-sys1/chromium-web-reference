[ContextualTasks] Bind service worker search IPC

Search communication between the browser and the AIM page previously
relied on document-scoped `ContextualTasksExtensionHandler` instances,
which required at least one extension iframe to be mounted on the page.
Extending the search Mojo channel with an optional `document_id` and
binding `ContextualTasksExtensionServiceWorkerHandler` on the component
extension's service worker allows the browser to exchange search
messages with `ContextualTasksWebContentsUserData` when zero extension
iframes are present.

Because a single profile-scoped service worker multiplexes messages
across tabs and side panels, incoming `document_id` tokens are validated
against `ExtensionApiFrameIdMap` to ensure the target frame is a primary
main frame in the same `Profile` before routing traffic.

[Autofill] AtMemory: Don't replace partial results with fetching message

When a `kPartialResponseSuccess` response with entries arrives, the
query stays pending, and the partial results should stay visible until
the final response arrives. However, they were replaced by the fetching
message in two cases:

1. While the popup is showing, the fetching timer kept running, and its
   next tick replaced the partial results. This CL stops the fetching
   timer whenever search results are shown.
2. With `kAutofillAtMemorySearchStatefulness`, reopening the popup while
   the search is still in progress restored the fetching state, even if
   partial results were already persisted. `GetStateForField()` now
   restores the partial results instead. To avoid mistaking the results
   of a previous search for partial results,
   `AtMemoryPersistedStateManager::OnFilterSubmitted()` now clears the
   persisted suggestions.

WebUILocationBar: Wait for toolbar page focus in BrowserFocusTest

With the WebUI location bar enabled, TestFocusTraversal() samples
IsViewFocused(VIEW_ID_OMNIBOX) after each FocusNextElement() step. That
reports the edit model's focus state, which only updates once the
toolbar page has sent its omnibox focus notification. FocusNextElement()
already flushes the toolbar pipes, but that flush is not always
sufficient: the page sends the notification from the omnibox input's
focus handler, and Blink only dispatches focus events once the page
itself is focused. Page focus (RenderWidgetHostImpl::SetPageFocus())
travels over the widget input pipe, which is not ordered with respect
to the frame interface used by SetInitialFocus() and by the flush. So
after tab traversal moves Views focus onto the toolbar WebView, the
flush can complete while the page is not yet focused, leaving a stale
omnibox focus state that makes the loop step past the omnibox and do an
extra lap.

to agree with the Views focused view before flushing the pipes, so all
callers observe the settled omnibox focus state. Also use the shared
GetWebUIToolbarWebView() helper.

focus-state transitions in WebUIReadOnlyOmnibox::OnTabChanged().

[pa] Trigger a memory pressure event when GigaCage is almost full

PartitionAlloc has a hard limit on memory that can be allocated: if an
allocation request doesn't fit in the GigaCage limits, the allocation
request fails, which (in Chromium) typically crashes the
application. There are known cases in the codebase (from field crashes)
where a renderer (or an extension) can trigger multiple GiB allocations
in the browser process, which can make it crash due to GigaCage
exhaustion.

An (imperfect) solution is to allow the GigaCage to communicate that
it's almost full to the application. This is what this CL does, namely:
- When the GigaCage gets 90% full, it calls an application-level
  function
- This function then triggers a critical memory pressure notification

To make this CL simpler, it only handles 64 bit POSIX builds. This
approach would likely not work on 32 bit builds anyway due to the
different GigaCage implementation and the address space layout. POSIX is
the only target in scope for this CL, as it makes code easier to review,
and I cannot test locally on Windows. However, a similar async-safe
notification mechanism exists on Windows, and will be added later.

[UnboundedElement] Constrain iframe bounds via permissions policy

This patch introduces the "unbounded-element" Permissions Policy
feature (with EnableForSelf default) to control whether an unbounded
element inside an iframe can extend beyond its embedding frame's
bounds. By default, cross-origin iframes cannot escape their frame
bounds unless the embedding frame delegates the "unbounded-element"
policy (e.g., <iframe allow="unbounded-element">). Same-origin iframes
escape by default unless restricted by an explicit container policy,
Permissions-Policy header, or sandbox attribute.

Chaining across nested iframes is supported by walking up the frame
tree and intersecting the bounds of any ancestor frame whose parent
does not permit "unbounded-element" escape.

Additionally, unbounded elements are constrained to the top-level main
frame (the renderer viewport and root view bounds) in two key cases:
1. When running on non-privileged open web pages, preventing content
   from overlapping browser chrome or escaping the window.
2. When an untrusted iframe is embedded inside a privileged WebUI page
   and delegated the "unbounded-element" policy. The iframe content can
   expand beyond its own iframe bounds, but remains strictly clamped
   within the top-level window so it cannot occlude UI such as the
   omnibox.

Theoretically, with this patch, open web usage is now safely bounded.
However, there are several bugs that came up during the review of this
patch, so the `UnsafeUnboundedElementOnTheOpenWeb` feature will be left
with the `Unsafe` prefix for now. For testing purposes, a new runtime
flag UnsafeEscapingUnboundedElementOnTheOpenWeb is introduced to permit
open web content to escape top-level window bounds. That one will
likely always be "Unsafe".

Bounds constraining is performed in both the renderer and browser:
1. In LayoutObject::AbsoluteBoundingBoxRectForUnboundedElement, which
   intersects the unbounded element's rect with any constraining local
   ancestor frame bounds and clips non-escaping frames to the root
   viewport.
2. In RenderWidgetHostViewBase::ConvertSubframeBoundsToScreen and
   RenderFrameHostImpl::GetUnboundedElementConstrainingBoundsInScreen,
   which enforce frame bounds constraints and clamp non-escaping frames
   to the root view's screen bounds.

[WebUI] Protect untrusted WebUI from tabnabbing

When a `chrome-untrusted://` page opens a blank popup, the synchronous
`about:blank` commit sets `last_successful_url_` to `about:blank` while
keeping the popup in the opener's `SiteInstance`. Because
`GetSiteInstanceForNavigation` previously fell back to the
`SiteInstance` site URL only when `last_successful_url_` was empty,
subsequent navigations to web URLs bypassed the WebUI security swap and
retained `window.opener`. Falling back to the `SiteInstance` site URL
when `last_successful_url_` is `about:blank` ensures a
`BrowsingInstance` swap that severs the opener reference.

As defense-in-depth, `UntrustedWebUINavigationThrottle` also blocks
unexpected cross-origin renderer-initiated navigations targeting frames
that currently host `chrome-untrusted://` documents. This prevents
cross-origin subframes or other non-ancestor frames from navigating an
untrusted WebUI frame to web content or `about:blank`.

Reland "[Android] Launch self-owned WebAPKs on renderer nav when unverified"

On Android S+, an unverified WebAPK is hidden from the MATCH_DEFAULT_ONLY
query Chrome runs during navigation interception. A renderer-initiated
click to an in-scope URL therefore stays in a Chrome tab even when Chrome
already owns that WebAPK and its menu shows Open rather than Install.
Incoming VIEW intents already recover via the sole-handler path; in-tab
clicks do not.

This change extends the existing non-default WebAPK handler query to
renderer-initiated navigations behind the new
WebApkSelfOwnedRendererNavLaunch feature, enabled by default as a Finch
kill switch. Chrome still keeps the MATCH_DEFAULT_ONLY resolver list as
the source of truth for chooser and implicit startActivity behavior. For
renderer navigations, Chrome first uses the in-memory WebappRegistry only
as a cheap origin precheck; if no registered WebAPK exists for the
destination origin, it skips the non-default PackageManager query.

When the precheck passes, the existing sole-handler path verifies the real
ResolveInfo, requires exactly one valid WebAPK, checks the user-level Open
supported links toggle, and launches via explicit Intent.setPackage. For
renderer intent:// URLs, the precheck and sole-handler query both use the
unpacked target URL rather than the original intent:// wrapper, so the
registry lookup matches the HTTPS WebAPK scope. The patch does not
synthesize ResolveInfo entries or merge WebappRegistry data into the
resolver list.

The same-host stay and intent-redirect keep-in-app gates still compare
default-only resolver lists first. If those gates would keep a renderer
navigation in Chrome, isNewSoleSelfOwnedWebApk checks whether the
destination is a newly discovered sole Chrome-owned WebAPK that did not
handle the previous / initial URL; in that case the stay gate returns
false so the sole-handler path can launch it.

shouldStayWithinHost also falls back to the referrer when the frame is on
its initial navigation and last-committed is null / empty / not HTTP(S),
which covers new-tab about:blank. This fallback is feature-guarded and
does not apply when there is a real different-host last-committed URL.

The user-visible change: a renderer-initiated click to a URL owned by
exactly one Chrome-installed WebAPK now opens that WebAPK even when
Android has marked it unverified, matching verified App Links behavior.
This applies both to cross-host navigations and to same-host clicks that
go from an out-of-scope URL to an in-scope one (the primary bug repro).

Reland notes: these WebAPK renderer-navigation tests exercise the
Android S+ non-default WebAPK query path. shouldQueryNonDefaultWebApks()

@MinAndroidSdkLevel(Build.VERSION_CODES.S).

testNonDefaultOnlyWebApkLaunchesOnRendererNavigationInNewTab timing out

the test can hit a known observer race (crbug.com/446837985): the
intercepted initial navigation closes the newly opened tab before the
navigation-failed callback is observed. This patchset keeps the new-tab
test disabled on DESKTOP to unblock the reland. Production
DesktopAndroidLinkCapturing behavior for WebAPKs / TWAs is tracked in
crbug.com/571579309.

Account for multiple AOT windows in full occlusion check

Update OccludedWidgetInputProtector CheckRectsOcclusion method to
evaluate full occlusion against the combined region of all visible and
historical Always-On-Top (AOT) widget bounds, rather than checking each
occluding widget in isolation.

Previously, full occlusion for non located events (such as key presses
on a view without custom protected bounds) assumed each AOT widget could
be evaluated independently, only blocking the event if a single AOT
widget contained the entire target view on its own. However, because
multiple AOT windows will soon be allowed to be present on screen at the
same time, the the assumption that there is only a single or isolated
AOT window does not hold.

Multiple AOT windows (or a combination of visible and historical AOT
bounds) could jointly cover an entire target view without any single
window containing it alone.

When checking for full occlusion, CheckRectsOcclusion now collects
visible and historical AOT bounds into an SkRegion, and blocks the event
if the combined region contains any target rect.

This change also adds corresponding unit and interactive UI tests
covering: adjacent AOT windows, overlapping AOT windows, unoccluded gaps
between AOT windows, and combined visible and historical occlusion.

[WebUI Toolbar] Rework IPH extension pop out handling.

This CL merges IPH (In-Product Help) and non-IPH pop out logic in
WebUIToolbarExtensionsContainer[Wrapper] classes. With this CL applied,
there may be only one pending pop out callback at a time. Requesting a
new non-IPH pop out cancels and pending (IPH or non-IPH) pop out,
while requesting an IPH pop out will do nothing if there's a pending
IPH or non-IPH pop out.

All pop out requests are solely for showing a popup, and two popups at
once doesn't really make much sense. The only non-IPH pop out caller
expects there to only be one pending pop out at a time, and this is
consistent with that logic.

The prefer-pre-existing IPH pop out behavior is more consistent with
Views, where all IPH requests but the first for a feature return
kAlreadyQueued (though there is a bug where we set
kExtensionsPinnedByDefaultElementId for both of them).

Preferring non-IPH requests to IPH is a new behavior - Views will try
to show both bubbles, and likely whatever was triggered second wins.
However, IPH promos are lower priority than potentially user-requested
popups, so it makes sense to favor non-IPH requests.

The ultimate goal here is to only have one pending pop out, prevent
that pop out's associated element from overflowing while the request is
pending, and then wait until only that element is visible before
showing the popout, instead of waiting for all elements to be visible,
since some may be hidden due to overflow logic.

[Rust CPSP] Fix CannotLockUsedProcessToSite death test in official builds

In official builds with `dcheck_always_on = true` (such as
`win-dcheck-tests`), C++ `CHECK_WILL_STREAM()` is true, so
`EXPECT_CHECK_DEATH_WITH` expects the stderr output to match the passed
regex. However, Rust is compiled with `-Cpanic=immediate-abort` in all
official builds (`is_official_build = true`) regardless of
`dcheck_always_on`, causing Rust `panic!` calls to trap immediately
without formatting or logging the panic message.

Update `ChildProcessSecurityPolicyTest.CannotLockUsedProcessToSite` to
expect an empty death message for the Rust path when `OFFICIAL_BUILD` is
defined.

[devtools] Remove legacy web tests covered elsewhere or obsolete

Delete 34 legacy http/tests/devtools/ web tests whose behaviour is
already covered by existing devtools-frontend unit or e2e tests, or by
inspector-protocol tests, plus a few tests that assert nothing useful
anymore. Each deletion was checked by comparing the legacy assertions
with the body of the covering test.

Covered by devtools-frontend unit tests:
- application-panel/resources-panel-idb-clear-for-storage-key.js
  (IndexedDBModel.test.ts)
- cache-storage/cache-deletion.js, cache-storage/cache-names.js
  (ServiceWorkerCacheModel.test.ts)
- compiler-script-mapping.js (CompilerScriptMapping.test.ts,
  SourceMapManager.test.ts)
- components/segmented-range.js (SegmentedRange.test.ts)
- console-cd.js (ConsoleContextSelector.test.ts,
  ConsolePrompt.test.ts)
- console/console-eval.js (ConsolePrompt.test.ts)
- console/console-log-wrapped-in-framework.js
  (ConsoleViewMessage.test.ts)
- coverage/coverage-repeated.js, coverage/coverage-view-filter.js
  (CoverageView.test.ts)
- extensions/extensions-headers.js, extensions/extensions-useragent.js
  (ExtensionServer.test.ts)
- network/network-request-revision-content.js (UISourceCode.test.ts)
- oopif/oopif-performance-cpu-profiles.js (RendererHandler.test.ts)
- resource-har-headers.js, resource-parameters.js (har/Log.test.ts)
- security/main-origin-assigned-despite-request-missing.js,
  security/origin-group-names-unique.js,
  security/security-unknown-resource.js
  (SecurityPanelSidebar.test.ts)
- security/mixed-content-reload.js,
  security/origin-view-ct-compliance.js,
  security/security-details-updated-with-security-state.js
  (SecurityPanel.test.ts)
- sources/debugger/debugger-minified-variables-evalution.js
  (NamesResolver.test.ts)
- webaudio/audio-context-selector-test.js (WebAudioView.test.ts)
- workspace-mapping.js (WorkspaceImpl.test.ts)

Covered by devtools-frontend e2e tests:
- console/console-search-reveals-messages.js (console/search.test.ts)
- console/console-tests.js (console/console-log.test.ts)
- inspect-element.js (elements/inspect-element.test.ts)

Covered by inspector-protocol tests:
- console/console-log-custom-elements.js
  (runtime/runtime-console-log-node-custom.js)

Obsolete:
- inspected-objects-not-overriden.js: DevTools no longer touches
  builtins in the inspected page (crbug.com/1050549).
- sources/debugger-pause/debugger-resume-button-in-overlay.js and
  sources/debugger-ui/selected-call-frame-after-formatting-source.js
  return early before asserting anything.
- test_runner/assertions-show-up-in-logs.js and unit/test-failure.js
  only test the legacy test harness itself.

The corresponding TestExpectations, SlowTests and MSANExpectations
entries are removed as well.
