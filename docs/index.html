[NTP] Clear fakebox text after forwarding pasted text to Omnibox

When a user pastes text into the NTP fake search box
(@id/search_box_text), NewTabPageCoordinator's TextWatcher forwards
the text to the real Omnibox via focusSearchBox(). Previously (prior
to crrev.com/c/8279777), afterTextChanged() cleared the fakebox text
via setSearchText(""). Without clearing it, the pasted text remained
visible in the NTP fakebox after navigating back from the Omnibox.

Restore mNtpSearchBox.setSearchText("") after focusSearchBox(), and
mark SearchBoxProperties.SEARCH_TEXT with skipEquality=true so
repeated pastes into the EditText (which mutate the Editable directly
without updating the PropertyModel) always clear the fakebox.

[base] Map Rust log::debug and log::trace to VLOG(1) and VLOG(2)

Currently, Rust log::debug! and log::trace! macros are mapped to
LOG(INFO), which causes them to be logged unconditionally to stderr
in DCHECK / debug builds.

This CL updates the Rust logger integration to map log::Level::Debug to
VLOG(1) and log::Level::Trace to VLOG(2). It also updates the FFI bridge
to check if verbose logging is enabled via GetVlogLevelHelper before
constructing LogMessage, preventing unintended log spam during tests
and standard runs.

Revert GTK module pinning on Linux

Per docs/security/x11-threat-model.md, a process with an X11 connection
is already treated as unsandboxed, so attacks that go through X server
state such as XSETTINGS are not security bugs. The mitigations below
were added for such reports. They cannot be complete, and they have
caused real regressions:

* Pinning gtk-modules unloaded GTK modules configured by KDE Plasma,
  crashing Chrome and Electron apps at startup (crbug.com/551107198).
* The GtkSettings::set_property interceptor crashed CFI builds
  (crbug.com/522820302).

This reverts the following, along with their tests:

* 513a1d1e5013c [ui/gtk] Sanitize gtk-modules in interceptor and install
  early (including unsetting GTK_MODULES)
* 9ec61d5e14fff [ui/gtk] Pin gtk-modules to an empty string during
  initialization
* 6209f630e1dea gtk: Disable CFI checks for GtkSettingsSetProperty to
  prevent crash

This also removes the now-unused GtkSettings interceptor. The
gtk_unittests target is kept, since it also covers the GDK fatal error
handling.

Report GPU watchdog progress between Graphite submit and wait

A sync Graphite submit both submits the pending work and waits for the
GPU to finish it. When both steps are long, the GPU watchdog can
mistake the combined time for a hang and kill the GPU process.

Split a SyncToCpu::kYes submit in GraphiteSharedContext::SubmitImpl()
into a submit(kNo) with the caller's submit info, followed by a
submit(kYes) that only waits. Call the new
GraphiteSharedContext::Delegate::ReportProgress() between the two so
the watchdog knows the GPU thread is making progress.

[🌺] Revert "settings: Enable SettingsInTabUrlNav by Default"

This reverts commit 159ed1f5fda8e0fc7ea6106beda11541579861eb.

Reason for revert: consistently fails chrome/try/android-internal-
desktop-x64-rel.

AutofillPaymentMethodsFragmentTest,
AutofillPaymentMethodsFragmentCardBenefitsTest,
AutofillIdentityDocsFragmentTest, AutofillProfilesFragmentTest,
CookieSettingsTest (17 tests) has failed in 4/4 recent builds of
chrome/try/android-internal-desktop-x64-rel, every attempt in every one
of them. This is not flake: it reproduces on every run, so it blocks the
CQ for every unrelated CL that touches this suite. The regression
appears at refs/heads/main@{#1708518}.

Example failing run:
https://ci.chromium.org/ui/p/chrome/builders/try/android-internal-desktop-x64-rel/28146

Enabling SettingsInTabUrlNav by default causes
SettingsNavigationFactory.createSettingsNavigation(Context) and
MultiColumnSettings.onPreferenceStartFragment() on desktop Android
(where SettingsInTab is enabled) to route sub-fragment navigation
through SettingsInTabNavigationDelegate.startSettings(), which calls
mTab.loadUrl(new LoadUrlParams(targetUrl)). In SettingsActivityTestRule
tests that host fragments in a MockTab without a WebContents,
MockTab.loadUrl() calls TabImpl.maybeShowNativePage() and
deterministically fails "assert webContents != null" at
TabImpl.java:2172 (or times out waiting for fragment attachment in
AutofillTestRule.waitForFragmentToBeShown).

Reverting to green the tree first. Please re-land once the failure is
understood and covered; this revert is about restoring CQ throughput,
not about the merit of the change.

[Extensions] Fix ScriptingAPITest restart test flake on Android

ScriptingAPITest.DynamicContentScriptsInjectInIncognito verifies that
dynamic content scripts registered in a PRE_ test persist and inject
correctly after a browser restart.

On Android, the browser is never shut down gracefully between the PRE_
and main test: the test process is killed after the PRE_ test and a new
one is started for the main test. The profile is therefore never
destroyed, and pending pref writes (which are batched on a 10 second
delay) only reach disk if that timer happens to fire before the process
is killed. If they didn't, the extensions loaded in the PRE_ test were
not restored after the restart and the test timed out waiting for them.

This change commits pending pref writes and flushes the
dynamic_user_scripts_store StateStore at the end of the PRE_ test. The
test body is scoped so that ScopedAllowHttpForHostnamesForTesting clears
the HTTP allowlist before the commit; otherwise the allowlist is
persisted and trips a DCHECK in the post-restart test.

It also removes the wait added in crrev.com/c/8327629, which addressed
the symptom rather than the cause. Extensions are loaded during startup,
and UserScriptListener already defers navigations until persisted
dynamic scripts are loaded, as long as prefs were saved.

Running the test 21 times with no retries on android-desktop-x64-rel
(via UTR), it failed 16 of 21 runs before this change and 0 of 21 after.

This also re-enables the test on Android, which was disabled in
crrev.com/c/8455518.

  runs that overlap the body region.

  keeping consecutive side-margin runs grouped across normal line

[Contextual Tasks] Deflake EphemeralToolbarButtonReopen

EphemeralToolbarButtonReopen flaked on win-rel (~0.5-0.7% across all
three UserVariations).

Root cause:
- The shared LensOverlayInteractiveTestBase::SelectRegionInLensOverlay
  helper drags with Kombucha's OS-level DragMouseTo(). On Windows,
  ui_controls sends mouse button events with SendInput and then waits,
  with no timeout, for the WM_LBUTTON* message to reach the UI thread's
  WH_MOUSE hook. Unlike mouse moves, button events have no fallback
  for occluding windows. When the message never arrives, DragMouseTo()
  hangs until the 90s sequence timeout. The failure logs show the
  overlay still in its preselection state with no region selected.
- This also affects every other caller of the helper on win-rel, with
  the same signature (step 21, DragMouseTo(), kSequenceTimedOut), e.g.
  ContextualTasksLensOverlayControllerInteractiveUiTest's
  LensSessionClosesOnSidePanelClose and
  LensSessionsCloseOnSidePanelClose_MultiTab.

- Send the region drag straight to the overlay renderer with
  content::SimulateMouseEvent() (mouse down, move, up) after
  WaitForHitTestData(), like SimulateLeftClickDrag in
  lens_overlay_controller_browsertest.cc. Unlike that helper, it skips
  RunUntilInputProcessed(), which blocks inside a Kombucha step. The
  drag still goes through Blink's pointer events and the overlay's
  region selection code; only the Windows input layer is skipped.
- Drop the now-unneeded MoveMouseTo(). Callers already wait for the
  drag's result (the Contextual Tasks side panel showing).
