base: Enable kStackScanMaxFramePointerToStackEndGap on Linux

When the sampling heap profiler (or another caller of
TraceStackFramePointers) runs on a WebAssembly JSPI secondary stack on
the main thread, GetStackEnd() returns __libc_stack_end (the end of the
main thread's initial stack). When unwinding reaches the root of the
secondary stack and falls back to ScanStackForNextFrame(), the scanner
can read past the top of the secondary stack into its adjacent PROT_NONE
guard page and crash with SIGSEGV.

Enable the existing ChromeOS workaround
(kStackScanMaxFramePointerToStackEndGap) by default on Linux so that
stack scanning aborts when the gap between the frame pointer and
stack_end exceeds the threshold.

Enabled-by-default-reason: fix Linux renderer crashes and keep a killswitch

[TopChrome] Update IsTopChromeWebUIURL()/IsForTopChromeWebUI() comments

The comment on ContentBrowserClient::IsTopChromeWebUIURL() currently
states that it identifies browser-chrome WebUIs so content/ can apply
process-sharing or metric-gathering logic, and cites Android as a
platform where it always returns false.

Process sharing across WebUIs is now controlled by
WebUIConfig::process_lock_host() (https://crrev.com/c/8689185 and
https://crrev.com/c/8690767). content/ only queries
IsTopChromeWebUIURL() with a SiteInstance's site URL to set
RenderProcessHost::IsForTopChromeWebUI() and to bypass spare renderers.
In Chrome, it returns true for trusted WebUIs that share the Top Chrome
process lock (https://crrev.com/c/8802633), which includes
chrome://tabstrip-ntb.top-chrome on Android.

This CL updates the comment to say what a Top Chrome WebUI is and to
point to RenderProcessHost::IsForTopChromeWebUI() for what it affects,
and drops the outdated Android example. The requirement that WebUIs
sharing a process lock return the same value (as for
IsWebUIBundledCodeCachingEnabled() in https://crrev.com/c/8739542) is
documented on the WebUIConfig constructor instead.

The comment on RenderProcessHost::IsForTopChromeWebUI() is outdated in
the same way: it states that WebUIs that share processes use it to avoid
sharing with non-Top Chrome WebUIs, and cites the same Android example.
This CL also updates it to describe when the value is set and what it is
used for.

[webrtc] Add RTCRtpSender::GenerateKeyFrame and sender attachment for script transforms

RTCRtpScriptTransform now records the RTCRtpSender it is attached to and
exposes GenerateKeyFrame(rid, callback), which runs on the main thread and
asks RTCRtpSender::GenerateKeyFrame to:
- reject (InvalidState) unless attached to a video sender,
- select all active layers (or the one matching `rid`), rejecting with
  NotFound when none remain (inactive encodings, ended track, rid not
  negotiated),
- stay pending for closed PC / stopped transceiver / non-sending direction
  / null track,
- instruct WebRTC to generate key frames for the selected layers.

The spec's "skip layers already pending" step is intentionally not
implemented (it can produce an unresolvable task); see comment.

No web-exposed change (the worker-side method lands separately).

Throttle BeginFrame on slower monitors on Windows

On multi-monitor Windows setups with mixed refresh rates,
VSyncThreadWin drives ExternalBeginFrameSourceWin at the primary
monitor's refresh rate (e.g. 240 Hz). Windows placed on a slower
secondary monitor (e.g. 60 Hz or 100 Hz) receive BeginFrames faster
than their swap chain can present, causing GPU presentation queues to
back up and stall.

Enable DisplayPrivate::SetVSyncDisplayID on Windows and notify
Compositor from WindowTreeHost::InitCompositor and
WindowTreeHost::OnHostDisplayChanged. In ExternalBeginFrameSourceWin,
query the window's current monitor VSync interval on creation and in
SetVSyncDisplayID, and throttle BeginFrame emission to match the
monitor's refresh interval when it is slower than VSyncThreadWin's
interval.

PrivateAI: Add expiration jitter to FeatureTokenManager refills

In Private AI, the server rounds blind-signed auth token expiration
times to 15-minute boundaries for privacy. Because FeatureTokenManager
scheduled its automatic cache refill at the exact server expiration
timestamp, all clients that fetched tokens in the same 15-minute window
refilled their caches at the exact same moment, causing traffic spikes
every 15 minutes.

Other token managers (such as IpProtectionTokenManagerImpl) avoid these
synchronized spikes by subtracting a random jitter interval from each
batch's expiration timestamp so clients refill ahead of the boundary at
spread-out times.

This CL subtracts a random jitter between 5 seconds and 15 minutes
(configurable via a feature parameter) from each token batch's
expiration time before scheduling the refill timer.

[Interop 2026] Require RTCSessionDescriptionInit.type

Per spec, `type` is a required member of RTCSessionDescriptionInit, and
the RTCSessionDescription constructor takes a non-optional
RTCSessionDescriptionInit argument. setLocalDescription() takes an
RTCLocalSessionDescriptionInit instead, where `type` is optional.

This CL:
* Makes the RTCSessionDescription constructor argument non-optional,
  so that RTCSessionDescription.length is 1.
* Throws a TypeError from the RTCSessionDescription constructor and
  rejects setRemoteDescription() (both promise and legacy-callback
  variants) with a TypeError if `type` is missing.
setLocalDescription() is unaffected.

`type` is not yet marked as required in the IDL. It is checked in C++ so
that the new behavior can be guarded by the
RTCRequireSessionDescriptionType runtime-enabled feature (status:
"experimental").

Making RTCSessionDescription.type and .sdp readonly is left for a
follow-up CL, since it cannot be guarded by a runtime-enabled feature.

Fixes RTCPeerConnection-setLocalDescription-parameterless.https.html
?interop-2026 and the "RTCSessionDescription interface object length"
subtest in webrtc/idlharness.https.window.html.

[Linux/X11] Dispatch keyup when GTK filters dead-key release events

On X11 keyboard layouts with dead keys (such as pt-br, es, and
us-intl), GtkIMContextSimple returns true for every GDK_KEY_RELEASE
while a dead-key or Multi_key compose sequence is active, without
re-injecting a fallback release event. InputMethodContextImplGtk
reported those release events as handled, and InputMethodAuraLinux
either dropped them (when TextInputType is NONE) or buffered them in
ime_filtered_key_event_ without dispatching a DOM keyup event, leaving
punctuation and modifier keys stuck pressed in web applications.

In InputMethodContextImplGtk::DispatchKeyEvent(), only treat a GTK3
KeyRelease as handled when an out-of-process IM module (IBus-GTK or
Fcitx-GTK) sets kPropertyKeyboardImeHandledFlag on the event state
(meaning the IME consumed the release or queued an async fallback
release via gdk_event_put()), and never treat GTK4
gtk_im_context_filter_key() release events as handled since GTK4 does
not re-queue fallback X11 events.

SeparateRendererBinary: Control separate renderer via a base::Feature

In Windows and Linux builds configured with
`enable_separate_renderer_binary = true`, allow selection between the
separate renderer binary and the main browser binary at runtime via the
`SeparateRendererBinary` feature (enabled by default). This allows
experimentation with the separate renderer binary via the variations
framework in a single build rather than requiring separate binary A/B
builds. macOS builds with `enable_separate_renderer_binary = true` does
not control anything meaningful yet after the Aperitif migration.

On Windows, `chrome.exe` selects `chrome_renderer.dll` in
`MainDllLoader` before `base::FeatureList` is initialized, so the
browser process evaluates `SeparateRendererBinary` when launching a
renderer from `chrome.exe` and forwards `--separate-renderer-binary`.
Staged Dynamic Patching modules (`ChildModuleManager`) take precedence
on both Windows and Linux without activating `SeparateRendererBinary`.

Based on https://crrev.com/c/8669463.

ash: Log warning when waiting on debugd in SchedulerConfigurationManager

SchedulerConfigurationManager previously waited on
DebugDaemonClient::WaitForServiceToBeAvailable() and
SetSchedulerConfigurationV2() replies with no timeout logging. When
debugd failed to start or respond on D-Bus, waiting callers such as
ARCVM and Crostini hung silently without indicating the cause in logs.

Add a 10s OneShotTimer in SchedulerConfigurationManager started for
WaitForServiceToBeAvailable() and restarted for each
SetSchedulerConfigurationV2() call to log a warning without changing
behavior or falling back to a default core count. Also extend
FakeDebugDaemonClient to support reporting unavailability and deferring
SetSchedulerConfigurationV2() replies in tests.

[NTP] Disable OneGoogleBar in WebUiNtpKeepAliveBrowserTest

The WebUI NTP lazily loads the OneGoogleBar inside a cross-site
chrome-untrusted://new-tab-page iframe. On slow builders like MSan,
that iframe loads during OpenNewTabPage() and claims the spare
renderer before ReuseWarmProcessAcrossTabsAndWindows checks that it
was not consumed.

Disable ntp_features::kNtpOneGoogleBar in WebUiNtpKeepAliveBrowserTest
so the unrelated cross-site subframe does not race with the
spare-renderer check, and re-enable the test on MSan.
