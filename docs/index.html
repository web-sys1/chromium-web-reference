[Contextual Tasks] Clear Lens region on composebox clear

When a region selected in the Lens overlay was attached to the
Contextual Tasks composebox as an "Ask about this image" chip, clearing
the composebox removed the chip but left the region selection drawn on
the overlay. ContextualTasksComposeboxHandler::ClearFiles() reset its
visual selection tokens without notifying the overlay.

ClearFiles() now clears the overlay's region selection when a visual
selection was attached, while keeping the overlay open so the user can
select a new region. Removing the chip directly through DeleteContext()
still closes the overlay, which is intended.

LensComposeboxController now also calls ClearRegionSelection() instead
of ClearAllSelections() when its visual selection chip is removed or its
files are cleared. This clears only the region selection and its
thumbnail, matching the scope of the removed context, rather than every
selection on the overlay.

Adds an interactive UI test that opens the overlay from the Contextual
Tasks composebox Lens button, selects a region, clicks the composebox
clear button, and verifies the region selection is cleared.

[CustomTabs] Deflake CustomTabActivityEphemeralTest#testNonInteractiveOmnibox

CustomTabActivityEphemeralTest.launchCustomTabActivity() called
CustomTabActivityTestRule.startCustomTabActivityWithIntent(), which
invokes waitForFirstFrame() and polls WebContents FrameInfo with a 3000ms
timeout. None of the tests calling launchCustomTabActivity() interact
with DOM elements in WebContents (testNonInteractiveOmnibox only clicks
the Android R.id.title_url_container view in CustomTabToolbar, and
testPopupCreationBlockedAndDoesNotCrashOnClose calls

renderer compositor FrameInfo updates can take over 3000ms after page
load, causing waitForFirstFrame() to time out.

Use startCustomTabActivityWithIntentNotWaitingForFirstFrame() in
launchCustomTabActivity(), remove the redundant waitForTabPageLoaded()
call in testNonInteractiveOmnibox(), dismiss the PageInfoController
dialog before tearDown(), and reset IncognitoReauthSettingUtils in
testIncognitoReauthPageNotShown().

[PublicTransit] Handle leftover CTS MockIme in SoftKeyboardCondition

On shared Swarming physical devices, a prior Android CTS test can leave
Settings.Secure.DEFAULT_INPUT_METHOD set to
com.android.cts.mockime/com.android.cts.mockime.MockIme without an
active MockImeSession. When a Public Transit test (such as
OmniboxDisplayStatePTTest or PublicTransitLeakTest#omniboxTest) calls
CtaPageStation.openOmnibox(), MockIme.onCreate() immediately throws
IllegalStateException ('Settings file is not found. Make sure
MockImeSession.create() is used to launch Mock IME') and crashes before
any soft keyboard window is shown.

Because CtaPageStation.openOmnibox() only enters SoftKeyboardFacility in
order to immediately close the soft keyboard via softKeyboard.close(),
teach SoftKeyboardCondition.determineIfSoftKeyboardShouldShow() to treat
a leftover com.android.cts.mockime default input method as not expected
to show a soft keyboard.

tracing: Don't always wait for the full timeout in shmem test

`TraceStartupSharedMemoryTest.PassSharedMemoryRegion` passes a
`base::WaitableEvent` to the IO-thread task that launches the child
process, but the task never signals it. The test thread therefore
always sleeps for the full `TestTimeouts::action_timeout()` (10s),
even though the child exits in well under a second on desktop.

Worse, when the child does time out, the task's `EXPECT`s fire after
the test has already returned and are reported against whichever test
runs next. On Android this shows up as `SnooperNodeTest` failures.

Signal the event once the child has exited, and wait for it without a
timeout. The task's own wait on the child is already bounded by
`action_timeout()`, and an untimed wait guarantees `wait` outlives the
task.

On Android the child crashes before running its test body, so the test
has never passed there. Now that the failure is reported correctly,
disable it on Android until that is fixed.

Locally on Linux this takes the test from 10001 ms to ~330 ms.

[CRD Linux] Terminate the logind session when desktop-session exits

pam_systemd moves the session processes started by
chrome-remote-desktop-x11-session@.service into the logind session
scope, so KillMode doesn't cover them, and cleanup() only kills
desktop-session's direct children. Daemonized processes, such as XDG
autostart apps, keep running after desktop-session exits. With the
default KillUserProcesses=no, logind then leaves the session in the
"closing" state indefinitely, and `loginctl terminate-session` becomes
a no-op.

Explicitly terminate the logind session via Session.Terminate after
cleanup(), while the session is still active, so that logind stops the
session scope. This is similar to how GDM's gnome-headless-session
terminates its sessions. SIGTERM and SIGHUP are ignored right before
the call, since terminating the session also signals desktop-session

ui: Decouple qr_code_generator dependency from chrome/browser/ui:ui

Previously, `static_library("ui")` in `//chrome/browser/ui` depended on

`//components/qr_code_generator` in its `public_deps`.

This caused Rust Crubit action
`//third_party/rust/qr_code/v2:cpp_api_from_rust_crubit_action` to be
propagated as an order-only dependency to `//chrome/browser/ui:ui`,
`//chrome/browser:core`, and `chrome_content_browser_client.cc`, blocking
up to 804 heavy C++ compilations until t = 111.23s on the critical path.

directly, and `browser_view.cc` only had dead unused includes of
`qrcode_generator_bubble_controller.h` and `qrcode_generator_bubble.h`.

dead includes from `browser_view.cc`, and move `qr_code_generator` from
`public_deps` to private `deps` in `//chrome/browser/ui/views/qrcode_generator`.
This completely unblocks `//chrome/browser:core` and
`chrome_content_browser_client.cc` from waiting for Rust Crubit actions.

blink: Isolate font_resource.cc to unblock core and downstream harddeps

In component('core'), loader/resource/font_resource.cc is the only
non-test translation unit that includes ift_patcher.h from
//third_party/blink/renderer/platform:font_rust_headers.

Having component('core') depend directly on :font_rust_headers adds
Crubit-generated font headers (font_format.h and ift_patcher_rs.h) to
core.harddeps, which propagates transitively through blink and content
to 4,102 targets and blocks 14,187 C++ compilation steps until Crubit
standard library and font bindings finish generating (~127s on a cold
build).

Split loader/resource/font_resource.h into
blink_core_sources('font_resource_header') and
loader/resource/font_resource.cc into blink_core_sources('font_resource')
with public = [] so that :font_rust_headers harddeps remain scoped to
font_resource.cc alone without adding any circular include exceptions
(reducing reachable .harddeps targets from 4,102 to 13).

Like :core_hot, these targets use the blink_core_sources template so that
they inherit core's common configs and deps from core.gni instead of
duplicating them. blink_core_sources now always creates a source_set for
header-only targets, since an empty static_library fails to be created
with lld-link /lib on Windows non-component builds.

[EVP] Require a bare host name in the DNS iss= record

The spec says the DNS delegation record carries `iss=` followed by the
issuer's host name (§3.1), and that the issuer identifier is "https://"
followed by that host, with no port, path or trailing slash, compared
byte-for-byte (§3.2):
https://dickhardt.github.io/email-verification/draft-hardt-email-verification.html#name-dns-delegation
https://dickhardt.github.io/email-verification/draft-hardt-email-verification.html#name-issuer-identifier

Chromium only checked that the value was non-empty and then passed it
through GURL, which silently normalized it: a port was kept in the
issuer identifier, a path was dropped, uppercase was lowercased, and a
query, fragment or userinfo was carried into the
.well-known/email-verification URL.

Now the record is rejected with kDnsInvalidRecord unless its value is
already exactly a canonical host. Existing issuers publish bare hosts
(e.g. iss=accounts.google.com) and are unaffected.

rebaselined with Skia Graphite enabled via
fieldtrial_testing_config.json (which enables SkiaGraphite and
SkiaGraphiteWinIntel on Windows).

In branded builds where fieldtrial_testing_config.json is disabled,
content_browsertests falls back to Skia Ganesh, which renders the
<textarea> rounded corners and diagonal resize grip lines without
antialiasing and causes FormControlsBrowserTest.Textarea to exceed the
average absolute error limit (13.91 vs 12.0).

Explicitly enable features::kSkiaGraphite and
features::kSkiaGraphiteWinIntel in FormControlsBrowserTest on Windows so
both branded and unbranded builds use the same Skia backend as the
Windows baselines.

[DeviceAuth] Cancel pending key fetch when the primary account changes

Previously, the service kept pending callbacks in a map keyed by Gaia
ID, aiming to track fetches for different accounts independently. Doing
this correctly is tricky, as the access token must be requested, and the
fetched keys stored and returned, for the right account across primary
account switches. This adds complexity for a rare scenario that doesn't
need more than failing the request.

This CL simplifies the service to only ever fetch for the current
primary account, which is much easier to reason about:
* Concurrent requests are still merged: at most one fetch is in flight,
and all callers' callbacks are queued and receive its result
* If the primary account changes or is cleared while a fetch is pending,
the service cancels the fetch and fails the queued callbacks. The
returned errors are not granular yet; this is addressed in a separate CL

For this:
* DeviceAuthorizationKeysFetcher gets a Cancel() API that drops the
  in-flight EndpointFetcher without running its callback.
* DeviceAuthorizationServiceImpl observes IdentityManager and handles
  primary account changes and IdentityManager shutdown.
* Since only the current primary account can have a pending fetch,
  DeviceAuthorizationServiceImpl stores the Gaia ID of that fetch and a
  single vector of callbacks, instead of a map keyed by Gaia ID.

[iOS] Account for App Bar in landscape TabGrid insets for Duo

When kChromeNextIa is enabled on iPhone Duo in the folded state, the
App Bar in landscape orientation docks along the leading or trailing
screen edge (AppBarPosition::kLeft or kRight). Previously,
TabGridViewController only accounted for bottom toolbar/app bar
heights when computing grid insets, causing grid content to overlap with
and become obscured by the side-positioned App Bar.
This change:
- Updates calculateInsetsForGridView in TabGridViewController to add
  AppBarHeightLandscape() to the left or right content insets when
  appBarPosition is kLeft or kRight.
- Observes layoutState:didChangeAppBarPosition: in TabGridViewController
  to dynamically re-calculate and apply grid view insets upon App Bar
  repositioning.
- In BaseGridViewController, converts physical UIEdgeInsets (left/right)
  to directional NSDirectionalEdgeInsets (leading/trailing) using
  UseRTLLayout(). Because NSCollectionLayoutSection sectionInsets are
  directional, passing physical insets directly would otherwise invert
  them in RTL languages.
- In GridLayout, invalidates the collection view layout when
  sectionInsets change so item sizes update immediately.
