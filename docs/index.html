Allow reentrancy in WebViewImpl::MainFrameLayoutUpdated()

When WebViewImpl::SetVisibilityState() iterates over observers_ and
invokes OnPageVisibilityChanged(), media observers such as
RendererWebMediaPlayerDelegate::OnPageVisibilityChanged() can
synchronously resume or pause playback. Updating WebVTT text track cue
displays during playback state changes can synchronously dispatch
blur/focusout events into script, which may read Element::innerText()
and force a synchronous style and layout update.

Document::LayoutUpdated() then calls
WebViewImpl::MainFrameLayoutUpdated() while SetVisibilityState() is
still iterating observers_, tripping the ObserverList reentrancy
DUMP_WILL_BE_CHECK.

Use NotifyAllowReentrancy() in MainFrameLayoutUpdated() so
DidUpdateMainFrameLayout() can be notified while another notification
(such as OnPageVisibilityChanged()) is already iterating observers_.

ExclusiveAccessManager accelerator delegation, and the corresponding
interactive UI tests behind BUILDFLAG(IS_MAC).

[Fusebox] Harden attachment reads; fail undecodable images locally

Multi-image gallery uploads of cloud-backed ("needs to be prepared")
photos intermittently fail with VALIDATION_FAILED /
IMAGE_PROCESSING_ERROR. That error is produced client-side when the
native image decode yields a null bitmap, which is consistent with the
Java fetcher forwarding empty or truncated bytes from the content
provider, or silently falling back to raw bytes after the platform
decoder already rejected them.

This change hardens FuseboxAttachmentDetailsFetcher:

* Read the content URI once and reuse the bytes for the C2PA sniff and
  for ImageDecoder.createSource(ByteBuffer). Previously the URI could be
  opened up to three times, which is costly and fragile for pipe-backed
  cloud media providers.
* Reject empty payloads locally (after one retry) instead of uploading
  them.
* Retry once when fewer bytes than the provider-reported SIZE are read;
  keep the longer read. Short reads are still forwarded because SIZE is
  not always authoritative, but they are now recorded.
* When AIM image downscaling is enabled and the platform decoder cannot
  decode the JPEG/PNG bytes, fail locally rather than forwarding
  full-resolution bytes that native decoding will reject the same way.
  OOM during downscaling still falls back to the raw bytes.
* Add Omnibox.MobileFusebox.AttachmentReadResult{.FileType} to make
  these outcomes visible.

The renderer's KeySystemsImpl lives as long as its RenderFrame, but the
browser's KeySystemSupportImpl is per document. When a frame navigates
away from its initial empty document, the RenderFrame is reused, the

statuses replaced by kDisconnectionError, so that the waiting queries
resolve and treat those capabilities as unsupported.

hangs if the document changes while the key system's lazy capability

never queried stays pending, and every query for it from the new

[ChroMenu] Fix potential UAF when updating zoom label text

When the zoom percentage changes while the app menu is open,
AppMenuZoomView updates `zoom_label_` via `Label::SetText()` and then
calls `AnnounceAlert()`.
On Windows, `Label::SetText()` synchronously raises a native
`kTextChanged` accessibility event (`UIA_Text_TextChangedEventId`),
which can spin the COM STA message pump and process an incoming UIA
request (such as `IExpandCollapseProvider::Collapse()` on the app menu
button) that closes and destroys the menu while `SetText()` and the
action-changed callback are still on the stack.
To prevent this re-entrant use-after-free:
1. Bind a `base::WeakPtr<AppMenuZoomView>` in the zoom label's action
   changed callback instead of an unowned raw pointer.
2. Wrap `label->SetText()` in a `views::ScopedAccessibilityEventBlocker`
   so the intermediate `kTextChanged` event is suppressed before the
   explicit `AnnounceAlert()` call at the end of the callback.

[glic] Harden EnforcesMaxCountLimits marketing page browsertest

In GlicMarketingPageTabHelperBrowserTest.EnforcesMaxCountLimits, the
test navigates to an allowed marketing URL to auto-open a Glic instance,
closes all embedders on that instance, and then opens a second tab to
verify that the auto-open impression limit prevents invoking Glic a
second time.

Because no conversation is registered and no user input is submitted on
that initial instance, calling CloseAllEmbedders() directly treats it as
a blank instance and starts the 1-second blank-instance cleanup timer
(kRemoveBlankInstanceDelay). On slower bots (such as Windows ASan or
when spawning a new renderer without a spare renderer), opening and
loading the second tab can take longer than 1 second. When that happens,
the cleanup timer fires mid-navigation and deletes the instance, causing
the final EXPECT_EQ(instance, GetInstanceImpl()) check to fail against a
null pointer.

Use CloseAllEmbeddersAndPreventDeletion(instance) when closing the Glic
UI between navigations so the instance stays alive regardless of how
long the subsequent tab creation takes.

Skip inline-style CSP checks for DOMParser-created documents

DOMParser.parseFromString() creates a Document with no browsing
context — it's never rendered or shown to the user. But style=""
attributes and <style> elements parsed into it were still checked
against the calling page's CSP, so a page with a strict style-src

content nobody ever sees.

(and previously unused) Document::IsDOMParserDocument() flag — the
same idea Chromium already applies to inline event handlers, which
skip their CSP check when there's no browsing context.

   - Replace 0k oq limits with an explicit 2k limit (2048)
   - Adjust the three dual-limit arms to sum to 60k instead of 62k:
     - Arm 1: Oq30kQ30k (30k oq, 30k q)
     - Arm 2: Oq1kQ59k (1k oq, 59k q)

- The 0k limits on "oq" only make sense if there's some mechanism to ensure that this truncation is only done when the "oq" value is the same as the "q" value. But I haven't implemented that yet.
- The 60k total is less likely to trigger the server-side 64k limit (we don't yet have a good measurement of how much "budget" we have after accounting for headers and cookies, so this is safer).

[masonry] Use per-segment rule visibility in grid-lanes

Before this change, `rule-visibility-items` in grid-lanes treated each
lane as a whole. A lane with any item made every segment next to it
occupied. The CSSWG resolved that rule visibility applies per segment in
grid-lanes too, so a segment next to empty space in a lane must be
treated as empty.

This change defines empty space through track openings. An opening is
the free space in a lane below an item. An opening is empty when no item
could align into it: there is no item above it, or the item above it has
zero available alignment space. A spec clarification for this definition
is pending, there is an open issue at
https://github.com/w3c/csswg-drafts/issues/14489#issuecomment-6132526774.

`GridLanesRunningPositions` already tracks openings and the item above
each one, but only for dense packing and stacking-axis alignment. It now
also tracks them when the container has gap decorations. The empty
openings are then stored per lane in the gap geometry, and paint checks
each rule segment against them.

[DTC] Add `screen_lock_secured` signal on Android

Populate `screen_lock_secured` in
AndroidSignalsCollector::GetOsSignals() using
KeyguardManager.isDeviceSecure(), queried synchronously via JNI from the
Android API:
https://developer.android.com/reference/android/app/KeyguardManager#isDeviceSecure().

The value is consumed by two features that use the device signals
aggregator on Android:
- Device Trust Connector (DTC): reported to the IdP as
  `screenLockSecured` during the real-time attestation handshake.
- Chrome Security Signals (CSS): included as `screen_lock_secured`.

isDeviceSecure() reports whether a PIN, pattern or password is set
(unlike isKeyguardSecure(), it does not count a locked SIM) and is
mapped to SettingValue::ENABLED / DISABLED. This API is already
exercised in several places in the Chromium repository, e.g.
`DeviceLockMediator`.

Implementation:
- Add DeviceSignalsUtils.java with a @CalledByNative isDeviceSecure().
  The KeyguardManager system service is asserted non-null rather than
  silently mapped to UNKNOWN: it should never be null, and other Chrome
  callers already rely on it being non-null.
- OsSecurityInfoProvider wraps the JNI call and returns the raw value.
  AndroidSignalsCollector now requires it in its constructor (the
  factory passes the real one, tests inject a mock) and maps it to
  ENABLED/DISABLED.

A follow-up CL will add a `disk_encryption` signal on top of the same
provider.

[Flex] Record column item expansion at block end

When a column flex item expands as a result of fragmentation, the
expansion is added to the line's item offset adjustment so that later
items in the column are pushed down. Previously, the expansion was only
recorded once the item had no outgoing break token. If the item reached
its block end but its content overflowed into the next fragmentainer, it
still had a break token, so later items in the column that were laid out
in the same fragmentainer did not account for the expansion and
overlapped the item.

This change records the expansion as soon as the item reaches its block
end. When the item later resumes at its block end to lay out its
overflow, the expansion is skipped, since it was already recorded in an
earlier fragmentainer.

There is no bug number associated with this, but I found this issue when
implementing similar functionality in grid lanes.

[IME] Speed up PlainTextRange::CreateRange()

Typing with an IME at the end of a large <textarea> was still very slow
after the GetCompositionCharacterBounds() fix
(https://chromium-review.googlesource.com/c/chromium/src/+/8543100).
Each composition update converts plain text offsets near the caret to
DOM ranges several times: TypingCommand::InsertText() and
InputMethodController::SetEditableSelectionOffsets() each do one, and
AddImeTextSpans() does one per IME text span. Each of these conversions
was quadratic in the number of lines.

To convert offsets to a range, PlainTextRange::CreateRangeFor() computed
the start and end positions of every text iterator run up to the end of
the range, although it only uses the positions from the run containing
the start onwards. The position of a newline emitted for a <br> is the
<br>'s index in its parent, which Node::NodeIndex() finds by counting
the <br>'s previous siblings. Until M138, a <textarea> kept its text in
a single Text node, so these positions were cheap to compute. M138
enabled the TextareaLineEndingsAsBr feature by default
(https://chromium-review.googlesource.com/c/chromium/src/+/6539226),
which represents each line break in a <textarea> with a <br>, so the
inner editor of a large textarea has thousands of <br> siblings.

CreateRangeFor() now skips computing the positions of the runs before
the one containing the start. The ranges it creates don't change and it
becomes linear in the length of the text before the range.

The new code is guarded by the FastPlainTextRangeCreateRange runtime
feature (enabled by default). The tests check that it creates the same
ranges as the legacy code for every pair of offsets in textareas, inputs
and contenteditables with line breaks, collapsible whitespace, surrogate
pairs and combining marks, including ranges past the end of the text.

Enable subframe error page isolation by default on Android

Following https://crrev.com/c/8511706, which enabled
IsolateSubframeErrorPages by default on all platforms other than
Android, enable it by default on Android as well. Low-memory Android
devices remain excluded: subframe error page isolation is turned off
whenever partial site isolation is disabled, which includes devices
below the partial site isolation memory threshold (see
https://crrev.com/c/8489916). Android WebView also remains unaffected,
since it disables error page isolation entirely.

Note that because Android doesn't use strict site isolation, this will
create out-of-process iframes for subframe error pages even when the
parent is in an unlocked process, where the security benefit is
smaller. We're accepting the resulting process count increase for now,
since subframe errors are a relatively uncommon case (e.g., network
errors or blocked navigations), and we can optimize this in a followup
(e.g., keep error pages in unlocked or shared ads processes) if metrics
show that it's a problem.

The fieldtrial testing config already enabled the feature on Android,
so Android bots have been running with it.

ContentPasswordManagerDriver::UserModifiedNonPasswordField forwarded
username candidates to PasswordManager without checking that the frame
is allowed to access password data for its URL, unlike the sibling
handlers (PasswordFormsParsed, PasswordFormSubmitted, etc.).

origin's URL. A compromised sandboxed iframe could therefore inject a
username candidate for its precursor origin's Username First Flow.

legitimate renderers also send this message from opaque-origin frames.

[NTP Aurora V2] Polish the ai mode section beside the MVT section

In the beside-MVT layout, the horizontal gap between the standalone AI
Mode card and the Most Visited Tiles container rendered as 16dp instead
of 8dp because ComposeplateCoordinator applied an extra 8dp end margin
to the inner AI Mode button (intended to separate buttons in the
horizontal composeplate bar) on top of the 8dp margin on the outer card
wrapper. That inner margin also shrank the visible AI Mode card from
88dp down to 80dp.

This CL skips the horizontal button-bar spacing update when the
beside-MVT layout is enabled and set a single 12dp end margin on the
outer AI Mode card container.

[Blink] Drop raster accesses in GPUCanvasContext::SnapshotInternal()

Removes the pre-copy and post-copy BeginRasterAccess()/EndAccess()
pairs, pre-copy UpdateDestructionSyncToken() call, post-copy
IsContextLost() checks, and raster_interface local variable in
GPUCanvasContext::SnapshotInternal().

This is a behavioral no-op:
- Because client_si is freshly created via sii->CreateSharedImage()
  immediately above (and the source wgpu::Texture is a Dawn texture on
  the webgpu interface), no operations on either resource have occurred
  on raster_interface. Passing client_si->creation_sync_token() directly
  to CopyTextureToSharedImage() (which passes it to
  BeginWebGPUTextureAccess() [1]) waits on the SharedImage creation
  token directly on webgpu without an unnecessary wait+gen round-trip
  through raster_interface.
- CopyTextureToSharedImage() ends its write access on client_si via
  WebGPUTextureScopedAccess::EndAccess() [2], which dissociates the
  mailbox and generates a completion SyncToken on webgpu. Updating
  client_si's destruction sync token [3] and calling
  AcceleratedStaticBitmapImage::CreateFromCanvasSharedImage() [4] with
  that SyncToken directly avoids a second unnecessary wait+gen
  round-trip through raster_interface.
- Removing the pre-copy client_si->UpdateDestructionSyncToken() [3] call
  is also a no-op: if CopyTextureToSharedImage() succeeds,
  client_si->UpdateDestructionSyncToken(sync_token.value()) immediately
  overwrites destruction_sync_token_ afterward; if it returns
  std::nullopt (which only happens if GetContextProviderWeakPtr() is
  null at entry), client_si is destroyed without ever having been
  accessed.
- SnapshotInternal() already checks
  shared_context_wrapper->ContextProvider().IsContextLost() above and no
  longer interacts with shared_context_wrapper's RasterInterface()
  afterwards, so the post-copy IsContextLost() checks are redundant.
