[TTC] Track the pointer in the session behind kTtcGetPointer

PointerTracker and PointerInputObserver exist but nothing creates them.
When kTtcGetPointer is enabled, SessionControllerImpl now owns a
tracker for the session and an observer for whichever contents are
voice-focused, recreating the observer as the focus moves between tabs
in the same way as the page context monitor. The tracker is cleared
when the focus moves, since positions are relative to the contents,
and PointerInputObserver now also clears it when the tab shows a new
page, since positions on the old page say nothing about the new one.

The session also remembers when the user's latest turn began: when
they start speaking or send text. ResolveLocations() needs that to
know which dwells belong to the current request. pointer_tracker() and
user_turn_start() expose both to the get_pointer tool, which a future
CL assembles.

The tracker's thresholds come from feature params on kTtcGetPointer,
so they can be tuned via Finch: dwell radius and duration, pre-turn
lookback, idle limit and max_results, the number of locations the tool
reports, clamped to at least one.

With the feature disabled nothing is created and the session is
unchanged.

Take the root render pass ID to avoid duplicates

When a viz clients submits a CompositorFrame to a new SurfaceId it
creates a new viz::Surface and ResolvedFrameData. The root render pass
ID from the previous ResolvedFrameData S1 is used in the new
ResolvedFrameData S2 to ensure root render pass IDs don't change. This
is to avoid reallocating buffers as they are linked to
AggregatedRenderPassId.

It's rare but possible that both S1 and S2 are drawn. The root render
pass for both S1 and S2 will have the same ID in this case resulting in
two AggregatedRenderPasses with same ID which is bad. Ensure this never
happens by resetting root render pass AggregatedPassId on S1 when S2
takes it.

[FlagsUI] Fix flaky RestartButtonTabOrder test in FlagsUiBrowserTest.App

`FlagsUiBrowserTest.App` runs in `browser_tests`, where multiple test
browser windows run in parallel and OS window focus is not guaranteed.
In Blink (`Document::SetFocusedElement`), programmatic `focus()` always
updates `getDeepActiveElement()`, but only dispatches a `blur` event on
the previously focused element when `FocusController::IsFocused()` is
true.

Consequently, `FlagsAppTest.RestartButtonTabOrder` had two focus-related
races:

When the browser window did not have OS focus, calling
`restartButton.focus()` from the `<select>` `Tab` keydown listener moved
`getDeepActiveElement()` to `restartButton` without firing `blur` on
`<select>`. Its `blur` listener (`eventTracker.removeAll()`) never ran,
so the second `Tab` keydown on `<select>` focused `restartButton` again
and failed `assertNotEquals(restartButton, ...)`.

and

Focusing `<select>` before `await simulateSelectChange(select, 1)` left
an async macrotask window (`microtasksFinished()`) during which losing
OS window focus fired a page-level `blur` on `<select>` and prematurely
removed the `Tab` keydown listener.

Fix this by focusing `<select>` after `await simulateSelectChange(...)`
and explicitly dispatching `blur` after the synthetic `Tab` keydown
events (which is a no-op when `focus()` already fired `blur` and ensures
the `blur` handler runs when the window is unfocused).

memory-safe Rust parser, NavigationInterceptor::ProcessRequest() must

during throttle check methods.

document becomes invalid beforehand nor moved across BindOnce(), and
remove the unused services/data_decoder include in
navigation_interceptor.h.

[TTC] Add the image annotator for get_pointer

get_pointer will show the model a small image of the page around where
the user pointed, with the pointed-at spot marked, so "what is this?"
can be answered about things the page content does not describe well.
AnnotatePointerImage() makes that image: it crops a viewport screenshot
to the rectangle ComputePointerCropRect() chose, draws a crosshair on
each pointed-at spot and encodes the result as a JPEG VisualContent for
the ToolResponse.

The marks are the WebUI prototype's: a red ring with a white halo, so
it stands out on any background, and a red crosshair. When several
spots are marked, each also gets a white badge with its number in red,
so the model can tell "this" from "that"; a single spot gets no badge,
since there is nothing to distinguish it from. Sizes are in DIPs and
scaled to the screenshot's device pixels, so the marks look the same
at every scale factor and the crop keeps the screenshot's resolution.

The function is pure and CPU-bound, and draws with Skia directly rather
than gfx::Canvas, whose fonts are not safe off the UI thread. The tool
will run it on the thread pool in a future CL.

[Android] Public Transit: Remove recheckActiveConditions()

recheckActiveConditions() spot-checked every Element enter Condition
of an ACTIVE state before some Transitions. It is unnecessary:

- Most callers trigger with clickTo()/longPressTo(), whose Espresso
  perform() already fails if the target View is gone.
- For press-back triggers, a drifted state fails the Transition: its
  exit Conditions are already fulfilled in preCheck().

It also had downsides: it reused Conditions outside of monitoring
(after onStopMonitoring()), so stateful Conditions such as Views with a
settle time could fail spuriously on a one-shot check; it contradicted
the documented contract that enter Conditions are not guaranteed to
stay true while ACTIVE; and it ran one blocking UI thread ViewFinder
pass per Element, which adds up for Stations with many Elements.

ConditionChecker had no other users, so it is removed as well.

Always queue DangerousDownloadDialog and use APP modal type

Previously, DangerousDownloadDialogBridge only queued dialogs when
WindowAndroid was null (or while a new window was launching during tab
reparenting on Shift+Click) and DangerousDownloadDialog only used
ModalDialogType.APP when kMaliciousApkDownloadCheck was enabled. For
generic dangerous file downloads (e.g. .swf, .crx, .cfg) or when the
feature flag was disabled, a null WindowAndroid during tab reparenting
caused the download to be silently removed without prompting the user.

In addition, DownloadController::CloseTabIfEmpty previously returned
early for all dangerous downloads because DangerousDownloadDialog used
ModalDialogType.TAB (which TabModalLifetimeHandler automatically
dismisses if its tab closes). Because DownloadUIController only calls
CloseTabIfEmpty once per download, blank tabs or windows opened for
dangerous downloads (e.g. via target="_blank" or Shift+Click) were
never closed.

This CL:
1. Removes the kMaliciousApkDownloadCheck gate on dialog queueing and
   ModalDialogType.APP in DangerousDownloadDialogBridge,
   DangerousDownloadDialog, and
   DownloadController::ShowDangerousDownloadDialog, and unifies
   DownloadController::OnDangerousDownload with
   ShowDangerousDownloadDialog. Because DangerousDownloadDialog is now
   always ModalDialogType.APP and re-queued if its host Activity
   closes, closing an empty initial-navigation tab or window will not
   cancel the dialog.
2. Narrows the early return in DownloadController::CloseTabIfEmpty to
   DOWNLOAD_DANGER_TYPE_SENSITIVE_CONTENT_WARNING (which still uses
   PolicyWarningDownloadDialog with ModalDialogType.TAB), allowing
   empty initial-navigation tabs to close for dangerous downloads
   handled by DangerousDownloadDialog.

If an act request fails before the task reaches kActing, the UI gets
no state change. Examples are a proto parse error, a task ID mismatch,
and a tool request that fails to convert. ActorUiStateManager then
keeps the cached step progress text, and the next act that sends no
new text shows the old text on the cursor chip.

- GlicActorClientSession::PerformActions now calls
  ActorTask::OnActRequested() on the current task before any check
  that can return early. UiEventDispatcher turns this call into a new
  TaskActRequested SyncUiEvent for ActorUiStateManager.

- ActorUiStateManager marks the cached text as used on the first act
  request after the text arrives. A second request without new text
  drops the text, so a failed act cannot leak its text into the next
  act. A retry that sends the same text shows the text again.
  While an act is in progress (kActing or kWaitingOnUser), a request
  leaves the text alone, because the text belongs to that act. For
  example, ActorTask::Act() rejects a request in kWaitingOnUser, and
  the waiting act shows its text again when it returns to kActing.

- Only the desktop cursor chip cache in ActorUiStateManager changes.
  ActorTask::step_progress() and the Android notification observers
  keep their current behavior.

get_pointer will answer "what is this?" with a small image of the page

[omnibox] Show the caret after an arrow key collapses a select-all.

Clicking into the Full WebUI omnibox selects all of the URL and shows
its start. Pressing [ArrowRight] (or [End]) then collapsed the selection
(into a single caret position), but for a URL that overflows the input,
left the caret out of view past the input's end.

`OmniboxPopupSearchboxElement.onInputWrapperKeydown()` collapses a
select-all for [ArrowLeft]/[ArrowRight]/[Home]/[End] itself, with
`setSelectionRange()`, before the key's default action. However, Blink
doesn't scroll a text field for `setSelectionRange()` and the default
action then has nowhere to move the caret (it's already at the start or
end), so `FrameSelection::Modify()` returns without revealing the
selection either.

Scroll the input to the start or the end of the text along with the
caret, like `selectRange()` and `SearchboxInputElement.updateInput_()`
do for programmatic selections. URLs are laid out LTR (the input and the
URL #mirror get dir="ltr") in RTL UIs too, but a query in an RTL script

it one more character to the left. Keys with modifiers (e.g. Alt+Left

Update WebUILocationBarInteractiveUiTest.UnelideCaretMove, which

Commit deferred value generators from the main-thread AnimationHost to
the compositor AnimationHost, and sample them through MutatorHost into
the sync tree's DeferredValueMap. A generator produces a value that
paint records by key and that a compositor animation updates without a
new commit.

  GenerateDeferredValueMap().
- Generators where CanRunOnImplThread() is false stay on the main
  thread. AnimationHost::SetDeferredValueGenerators() copies the rest,
  and requests a commit only if the copy changed.
- SyncFrom() updates the copy in place. It keeps a generator whose
  source is unchanged, so its progress and cached sample survive a
  commit.
- UpdateValues() updates the map in place and returns each key that
  gains, loses, or changes its value. A tick of a running animation
  only overwrites colors.
- Activation copies the map to the active tree. The pending tree keeps
  its map, so when it is recycled it diffs against what the active
  tree has.

AnimationHost::SetDeferredValueGeneratorProgress() so far. The next CL
adds their callers. Nothing calls SetDeferredValueGenerators() yet, so
there is no behavior change.

still advancing `nextAnnotationId_` so valid annotation IDs remain in
