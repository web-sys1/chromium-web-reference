[browser_actuator] Show session history on the internals page

chrome://browser-actuator-internals now shows every recorded
transport session and its messages, using GetSessionHistory() from
the parent CL 8445676.

- The page loads the history once when it opens. Reloading the tab
  shows new data. Live updates will be implemented in a follow-up.
- One card per session: ID, active or closed, start and end time,
  and downstream and upstream counts.
- Session events are in a collapsible details element, closed by
  default, showing "Events (N)" or "Events (showing N of M)".
- Directions are shown as "Downstream" and "Upstream".
- Each event lists time, direction, payload types, and message text.
- Messages longer than 80 characters are collapsible with a preview.
  Message text is bound as text, never as HTML. A marker shows when
  the browser cut a message to its 8 KB limit.
- The hard-coded "Disconnected" transport badge is removed. This can
  be inferred from session status.

Messages can contain page context from the actuation payload. They
are shown only in this trusted WebUI, which is gated behind
kBrowserActuatorInternals.

A mock link of the page can be found in the comment section of bug
555334390.

`ui/android/resources`:

  to 3 via `base::SpanWriter` and `base::SpanReader`, and use
  `std::bit_ceil` / `base::bits::AlignUp`.

  fields to eliminate 4 bytes of internal padding.

  redundant lookups in `GetStaticResourceWithTint` and
  `OnFrameUpdatesFinished`, use `@JniType("SkBitmap")`, and remove
  unused resource APIs.

dialog before tearDown(), and reset IncognitoReauthSettingUtils in
testIncognitoReauthPageNotShown().

Avoid creating the shared D-Bus session bus in DynamicLauncherPortal

DynamicLauncherPortal checked whether it was using the shared session
bus by comparing its bus with dbus_thread_linux::GetSharedSessionBus(),
which creates the shared bus if it doesn't exist yet. When a custom bus
was passed in (as in unit tests), this created a shared bus bound to the
test's task environment that outlived the test. A later test in the
same process that shuts down the shared bus (e.g. via
RenderViewHostTestHarness::TearDown()) then crashed with a dangling
raw_ptr, e.g. when EyeDropperPortalTest ran after

[PWA] Fix origin association backfill landing in the future

When an app has no origin_association_last_validation_check_time, the
command backfills one. The comment says to randomize it "in the past to
ensure no network fetch spikes", but the code computed
Now() + delta + base::Days(1), which is 1-2 days in the future.

Combined with the 24h throttle below, that defers the first real
revalidation to Now() + delta + 2 days -- 2 to 3 days out, rather than
the intended 0 to 1. A revoked scope extension therefore stays trusted
about two days longer than the throttle promises, on every launch path,
for any app whose timestamp is unset.

- base::Days(1) is what the surrounding code describes: the stored time
lands in [now - 1 day, now], and the throttle turns that into a first
fetch at a uniformly random point within 24 hours, which is what spreads
the load.

The existing test asserted the bug rather than the intent:

  // The time should be within the last 10 days.
  EXPECT_GE(*app->origin_association_last_validation_check_time(),
            clock().Now());

The comment says the past; the assertion required the future. Assert both
bounds instead, so the offset cannot silently flip sign again, and add
NotThrottledWithinADayOfBackfill to cover the property that actually
matters -- that a backfilled app becomes eligible within a day. Both tests
fail against the previous arithmetic.

The stray "10 days" predates the throttle being 24h and is dropped.

ui: Decouple qr_code_generator dependency from chrome/browser/ui:ui

Previously, `static_library("ui")` in `//chrome/browser/ui` depended on
both `//components/qr_code_generator:bitmap_generator` and
`//chrome/browser/ui/views/qrcode_generator`. Furthermore,
`//chrome/browser/ui/views/qrcode_generator` exposed
`//components/qr_code_generator` in its `public_deps`.

This caused Rust Crubit action
`//third_party/rust/qr_code/v2:cpp_api_from_rust_crubit_action` to be
propagated as an order-only dependency to `//chrome/browser/ui:ui`,
`//chrome/browser:core`, and `chrome_content_browser_client.cc`, blocking
up to 804 heavy C++ compilations until t = 111.23s on the critical path.

However, `static_library("ui")` does not use `bitmap_generator.h`
directly, and `browser_view.cc` only had dead unused includes of
`qrcode_generator_bubble_controller.h` and `qrcode_generator_bubble.h`.

Remove the unused dependencies from `//chrome/browser/ui:ui`, remove the
dead includes from `browser_view.cc`, and move `qr_code_generator` from
`public_deps` to private `deps` in `//chrome/browser/ui/views/qrcode_generator`.
This completely unblocks `//chrome/browser:core` and
`chrome_content_browser_client.cc` from waiting for Rust Crubit actions.

[TabModel] Consolidate onTabGroup* callbacks onto TabGroupObserver

TabModelObserver previously duplicated tab group lifecycle callbacks
(onTabGroupCreated, onTabGroupRemoving, onTabGroupMoved, and
onTabGroupVisualsChanged) alongside TabGroupObserver solely so
TabModelObserverJniBridge could forward group events to native
observers. This forced TabCollectionTabModelImpl to iterate all
registered TabModelObservers on every tab group creation, move, visual
update, and removal even though TabModelObserverJniBridge was the only
consumer.

Have TabModelObserverJniBridge implement TabGroupObserver directly, move
onTabGroupVisualsChanged to TabGroupObserver, and remove the duplicate
callbacks and observer loops from TabModelObserver and
TabCollectionTabModelImpl. Routing willRemoveTabGroup through
TabModelObserverJniBridge also ensures native observers receive
OnTabGroupRemoving when a tab group is dissolved via ungrouping,
merging, or group creation undo.

[Extensions] Fix ScriptInjectionTracker desync for RequestContentScript

Previously, RequestContentScript::InstructRenderProcessToInject() used
PermissionsData::CanAccessPage() to check if an extension could inject a
declarative content script into a frame. Because CanAccessPage() returns
true even when host permissions are withheld, the browser invoked
ScriptInjectionTracker::WillExecuteCode() prematurely before sending
ExecuteDeclarativeScript() to the renderer. In the renderer,
ScriptInjection::TryToInject() detected that permissions were withheld
and deferred execution. This caused the browser and renderer states to
desynchronize: the browser erroneously considered the renderer process
as having executed the extension's content script even though no script
ran.

With this change, the browser does not update ScriptInjectionTracker
when page access is withheld during declarative content script
evaluation. Instead, the renderer defers the script and requests
permission via ExtensionActionRunner. Once the user explicitly grants
permission on the tab, the deferred script executes in the renderer and
ScriptInjectionTracker is updated so browser and renderer states remain
synchronized.

We update RequestContentScript::InstructRenderProcessToInject() to query
PermissionsData::GetPageAccess() directly and only call
ScriptInjectionTracker::WillExecuteCode() when access is kAllowed. We
also add mojom::InjectionType::kDeclarativeScript, which
UserScriptInjector reports for RequestContentScript scripts, and have
ExtensionActionRunner gate it on PermissionsData::GetPageAccess() so
withheld requests are queued. ExtensionActionRunner already notifies
ScriptInjectionTracker before permitting pending scripts to execute.

Views HomeButton on macOS.

The native HomeButton only accepts drops that carry a URL. On macOS,
ui::clipboard_util::URLsAndTitlesFromPasteboard() already synthesizes a

`text/uri-list` and are routed to OnHomeButtonDropUrl(). A drop that is

ignores it regardless of where the drag started.

every `text/plain`-only drop, and consumes the pending drag origin state
so it does not leak into later navigations.

by the email sent from the settings page. The page is refreshed when the
signed-in accounts change (e.g. OnPrimaryAccountChanged() on sign-out),
but the request is asynchronous and can race with the account being
removed, and the email is renderer-provided. When the lookup fails it
returns an empty AccountInfo, and the handler went on to use an empty

- SetChromeSigninInterceptionUserChoice() stored the choice under an

  hit CHECK(!gaia_id.empty()) in SigninPrefs::ClearPref() and crashed
  the browser.

Return early when the account is not found, before any pref write or
histogram recording.

openURLInNewTab: creates an active WebState and inserts it into
WebStateList, synchronously triggering WebStateListDidChange in
SendTabToSelfBrowserAgent. If the entry is not yet marked opened in the
model, the browser agent treats it as unopened and opens a duplicate
background tab while emitting a duplicate outcome sample.

Marking the entry opened and activated in the model before dispatching
openURLInNewTab: prevents this reentrancy issue.

[DeviceAuth] Cancel pending key fetch when the primary account changes

Previously, the service kept pending callbacks in a map keyed by Gaia
ID, aiming to track fetches for different accounts independently. Doing
this correctly is tricky, as the access token must be requested, and the
fetched keys stored and returned, for the right account across primary
account switches. This adds complexity for a rare scenario that doesn't
need more than failing the request.

This CL simplifies the service to only ever fetch for the current
primary account, which is much easier to reason about:
* Concurrent requests are still merged: at most one fetch is in flight,
and all callers' callbacks are queued and receive its result
* If the primary account changes or is cleared while a fetch is pending,
the service cancels the fetch and fails the queued callbacks. The
returned errors are not granular yet; this is addressed in a separate CL

For this:
* DeviceAuthorizationKeysFetcher gets a Cancel() API that drops the
  in-flight EndpointFetcher without running its callback.
* DeviceAuthorizationServiceImpl observes IdentityManager and handles
  primary account changes and IdentityManager shutdown.
* Since only the current primary account can have a pending fetch,
  DeviceAuthorizationServiceImpl stores the Gaia ID of that fetch and a
  single vector of callbacks, instead of a map keyed by Gaia ID.
