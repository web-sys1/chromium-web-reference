Defer non-initial BrowserView layout calculations while invisible

During early startup, the main browser window is created invisible
before being shown. As startup components initialize, they request
layout passes on BrowserView. Running layout calculations while the
window is invisible is completely redundant (except for the very first
one to get sizing info etc), because nothing is presented to the user,
and it blocks the UI thread during critical startup navigation of
the WebUI toolbar etc.

This is heavily triggered by the asynchronous loading of the WebUI
Toolbar:
1. The WebUI Renderer process loads page resources asynchronously,
   altering its DOM layout and sending size changes or document load
   milestones to the Browser process over Mojo IPC.
2. In the Browser process, WebUIToolbarWebView handles these Mojo
   messages, invoking PreferredSizeChanged() which calls
   InvalidateLayout().
3. This invalidation bubbles up to BrowserView, which asynchronously
   posts a layout task to the Browser main thread message loop.
4. On the next frame tick, Widget::LayoutRootViewIfNecessary executes a
   full BrowserView::Layout pass.

In the unoptimized baseline, this triggers 9 layout passes:
- 1 initial pass during window creation (to establish starting bounds).
- 7 intermediate redundant passes during navigation while invisible.
- 1 visible flush pass when the window is shown.

This CL introduces features::kDeferLayoutDuringBrowserStartup, which:
1. Skips any layout passes after the very first initial layout
   pass, as long as the browser window is invisible during startup.
2. Tracks the layout state using a StartupLayoutState enum (kInitial,
   kDeferring, kDisabled).
3. If layout requests were deferred, we clear the deferred state and
   trigger exactly one combined layout pass immediately when the window
   transitions to visible inside
   BrowserView::OnWidgetVisibilityChanged().

This coalesces the 7 intermediate redundant layout passes into the final
show pass, reducing the total layout passes from 9 down to 2, saving
UI thread blocking time on macOS and Windows during startup.

Performance Impact:
* Windows (25 runs, Warm Startup):
  - FCP (Active Tab First Paint): -26.11 ms (p=0.0129) 🟢
  - Reload Paint (Reload Button First Paint): -26.07 ms (p=0.0132) 🟢
  - Compositor Frame Submissions:
    * Browser Window: -19.97 ms
    * WebUI Toolbar: -16.81 ms
    * Active Tab: -20.39 ms

* macOS (10 runs, Warm Startup):
  - FCP (Active Tab First Paint): -67.18 ms (trend)
  - Reload Paint (Reload Button First Paint): -62.20 ms (trend)
  - Compositor Frame Submissions:
    * Browser Window: -11.85 ms
    * WebUI Toolbar: -49.80 ms
    * Active Tab: -45.14 ms
