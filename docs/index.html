[X11] Only disable _GTK_FRAME_EXTENTS on Xfwm4 releases older than 4.17

X11Window::CanSetDecorationInsets() unconditionally returned false on
Xfwm4 because releases before 4.17.0 did not handle removal of
_GTK_FRAME_EXTENTS, causing maximized windows to be larger than the
screen.  That was fixed in xfwm4 commit 488288f6, first released in
4.17.0.  A previous attempt to remove the workaround entirely was
reverted because Ubuntu 20.04/22.04 still ship xfwm4 4.14/4.16.

Xfwm4 does not publish its version, but commit c26c9394 (a descendant
of 488288f6, also first released in 4.17.0) removed
_NET_SYSTEM_TRAY_OPCODE from _NET_SUPPORTED.  Every older release
advertises it unconditionally.  Use that to keep the workaround only
for affected Xfwm4 versions.

This fixes frameless windows (e.g. Electron 43+ apps such as VS Code)
drawing an opaque resize band instead of client-side shadows on modern
Xfce.

Check IsContextDestroyed() before optimizing stream transfer

If a transferred `MediaStreamTrackProcessor.readable` stream is
deserialized after the destination `ExecutionContext` has already been
destroyed, `TransferredFrameQueueUnderlyingSource` never receives
`ContextDestroyed()`, so `ClearTransferredSource()` never runs on the
host `FrameQueueUnderlyingSource`. The host then continues forwarding
frames to the destroyed worker's heap.

Check `context->IsContextDestroyed()` in
`FrameQueueTransferringOptimizer::PerformInProcessOptimization()` and
bail out early instead of creating the transferred source.

[updater] Report COMMAND_STATUS_ERROR when an app command times out

LegacyAppCommandWebImpl::get_status derived COMMAND_STATUS_COMPLETE from
AppCommandRunner's completion event, which is also signaled when the
runner gives up monitoring after kWaitForAppInstaller (15 minutes). The
child is intentionally not killed on timeout, so get_exitCode, which
queried the live process, returned S_FALSE without setting the
out-param. Clients that poll for COMPLETE and then check
SUCCEEDED(get_exitCode) consequently reported an exit code of 0 for
commands that had actually timed out.

AppCommandRunner now records the exit code before signaling completion,
only when the process exits while being monitored. get_status,
get_exitCode, and the telemetry ping all use this recorded value:
- COMPLETE and S_OK with the exit code if the command exited in time.
- COMMAND_STATUS_ERROR and S_FALSE if monitoring timed out. This is
  latched and does not change if the child exits later.

The ping task waits for the runner via a new AppCommandRunner::Wait(),
which is bounded by the monitoring timeout.

The timeout remains non-fatal to the child process. The monitoring
timeout can be shortened in tests via
AppCommandRunner::SetTimeoutForTesting.

surface-embed: do not force SurfaceLayer contents opaque

Previously, SurfaceEmbedWebPlugin forced SetContentsOpaque(true) on its
cc::SurfaceLayer. Removing it aligns with how GuestView paints
uncommitted frames and fixes two issues:

1. Fixes the blue box shown in debug builds (e.g. in `webui_examples
   --webshell`) before a child WebContents commits its first frame.
   When a surface is uncommitted, Viz substitutes a transparent fallback
   quad; marking the layer opaque caused Viz's debug-only check to flag
   the mismatch and draw bright blue instead.
2. Enables transparent and semi-transparent child WebContents documents.
   When the child view's background is set to transparent, leaving the
   SurfaceLayer non-opaque allows Viz to alpha-blend the child content
   over the parent page.

[css] Avoid synchronous style update in SpellChecker when no markers exist

When `contenteditable` is removed or set to false,
HTMLElement::AttributeChanged invokes
SpellChecker::RemoveSpellingAndGrammarMarkers(..., kOnlyNonEditable) to
strip leftover misspelling markers from nodes that are no longer
editable.

Because toggling `contenteditable` changes inherited
`-webkit-user-modify`, the element's subtree is marked dirty for style
recalc. Calling UpdateStyleAndLayoutTreeForElement() then forces an
immediate synchronous style update.

Skipping the forced call to UpdateStyleAndLayoutTreeForElement will
likely trigger a relayout later-on since the tree is dirty (resulting in
the same amount of work), but it has a few benefits:
- Multiple calls to RemoveSpellingAndGrammarMarkers would result into
at most 1 relayout
- Hidden content won't need to relayout at all

[a11y] Validate renderer-provided AXNodeIDs at browser entry points

Previously, crrev.com/c/7727677 added AXNodeID validation in shared
StructTraits<AXNodeData>::Read and StructTraits<AXTreeUpdate>::Read.
However, because AXTreeUpdate and AXNodeData are used bidirectionally
(such as Browser -> ChromeOS Extension Renderer in automation and
reading mode), those StructTraits checks caused valid browser-generated
negative internal node IDs to be rejected when sent to ChromeOS
extensions, and were reverted in crrev.com/c/8250159 and
crrev.com/c/8288690.

This CL reintroduces browser-side validation of renderer-provided
AXNodeIDs specifically at untrusted browser-side entry points, avoiding
the bidirectional StructTraits deserialization path: 1.
RenderAccessibilityHost::HandleAXEvents and HandleAXLocationChanges
(covers all web renderers and PDF renderers via
blink.mojom.RenderAccessibilityHost), with defense-in-depth checks also
in RenderFrameHostImpl. 2. AXMediaAppUntrustedService::OnPageOcred
(ScreenAI OCR utility output). ReadAnythingUntrustedPageHandler was
already validated in crrev.com/c/7795304.

To support this cleanly, validation helper functions are added to
ui/accessibility:
- IsValidAXNodeDataFromRenderer
- IsValidAXTreeUpdateFromRenderer
- IsValidAXLocationAndScrollUpdatesFromRenderer
- IsValidAXUpdatesAndEventsFromRenderer

Unit and browser tests are added to verify that invalid IDs trigger a
Mojo bad message or are rejected.

[variations] Only dump for large seeds after seed validation

Previously, Uncompress() in variations_seed_store.cc called
base::debug::DumpWithoutCrashing() whenever the 4-byte ISIZE
gzip trailer reported a value above 40 MiB (introduced in
crrev.com/c/7907587). Because GetUncompressedSize() reads the
last 4 bytes of the buffer before checking the 50 MiB ceiling,
decompressing, or validating the seed, any corrupt, truncated,
or intercepted payload had a ~99% probability of triggering a
false-positive crash dump.

Extract the 40 MiB check into a helper function
MaybeDumpIfSeedSizeApproachingLimit() next to Uncompress() and
call it in VariationsSeedStore::ProcessSeedData() after
ValidateSeedBytes() succeeds, ensuring dumps are only generated
when authentic, validated variations seeds approach the 50 MiB
uncompressed size limit.
