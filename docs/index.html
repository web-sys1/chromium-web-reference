Restore mouse cursor for native dialogs on Windows

When the mouse cursor is hidden while typing, native dialogs can inherit
a hidden cursor because: 1. Calling ::ShowCursor(FALSE) in
DesktopWindowTreeHostWin decrements the
   Win32 thread-global cursor counter below 0.
2. Mouse events over native dialogs bypass Chrome's event filter, so
   Chrome never unhides the cursor.

This CL fixes this by: 1. Stopping ::ShowCursor() calls in
DesktopWindowTreeHostWin (per-window
   visibility is already handled via CursorType::kNone).
   This is most likely legacy code that is no longer necessary.
2. Restoring cursor visibility in HandleCancelMode() when a modal dialog
   opens, so the cursor is restored immediately without mouse movement
   and CursorClient stays in sync.
3. Guarding these changes behind features::kHideCursorWhileTyping, so
  that if this ever causes a regression, we can disable it to diagnose
  the issue.

[NTP Customization Sync] Normalize NTP background URL options in theme translation

When NtpBackgroundService constructs theme collection image URLs from
the Backdrop service, it appends platform-specific FIFE image options
via GetImageOptions():
- Android & iOS: =s2556-k-no-nd
- Desktop: =w3840-h2160-p-k-no-nd-mv

Previously, TranslateDesktop, TranslateIos, and TranslateAndroid in
theme_translation.cc copied ntp_background() verbatim without replacing
the source platform's URL options suffix with the local platform's
GetImageOptions(). Because downstream consumers compare full URL strings
directly, the mismatched suffix caused cross-platform theme equality
checks, theme history deduplication, active theme collection selection
highlighting, and Backdrop URL validation to fail between Desktop and
Mobile.

This CL:
1. Adds NormalizeNtpBackgroundUrl() in theme_translation.cc to strip any
   existing image options via RemoveOptionsFromImageURL() and append the
   local platform's GetImageOptions() via AddOptionsToImageURL() across
   TranslateDesktop, TranslateIos, and TranslateAndroid. Only valid
   HTTP(S) URLs of theme collection backgrounds (non-empty
   collection_id) are normalized; everything else is left unchanged.
2. Moves the image URL option helpers (GetImageOptions(),
   GetThumbnailImageOptions(), AddOptionsToImageURL(),
   RemoveOptionsFromImageURL()) from components/themes/ntp_background_data
   into a new foundational //components/themes/common target, so that
   //components/themes/cross_device can depend on them without a
   child -> parent directory dependency. ntp_background_data.h still
   includes the new header, so existing callers are unaffected.
3. Adds unit tests in cross_device_theme_tracker_unittest.cc verifying
   cross-platform URL normalization and theme equality, and that
   empty/unset, non-HTTP(S), invalid, and non-collection URLs are left
   unchanged.

MaybeScheduleEvictionUntilSystemHealthy() computed `total_memory_usage`
once and never updated it inside the loop. So whenever paging was
triggered, every populated item was paged to disk regardless of the
limit.

expected usage is at or below the limit. Paging now happens in smaller,
more frequent batches. The pressure-triggered flush (limit of 0) is
unaffected.

a follow-up. Its test expectations are only updated here to match the

Ignore default-value pref writes when no cross-device entry exists

Calling PrefService::Set* with a value equal to the registered default
stores an entry in the user pref store (so IsDefaultValue() returns
false) even when the effective value did not change from default (e.g.
during startup initialization).

Skip recording or propagating a cross-device pref entry when no entry
exists for the local device and the current value equals the default
pref value.

This means if a device writes a pref with a default value as part of
startup (which happens with the omnibox preference on Android),
GetBestMatchDevice methods will not count that as a true written
preference.

This bug was not relevant until after crrev.com/c/8530633 was submitted
because it used to be the case that CrossDevicePrefTracker was
instantiated after the omnibox preference was already written (which
meant that the "observed change count" for the current device would not
be incremented to 1).

[Android] Restore page focus when a tab-modal dialog closes

TabModalPresenter.saveOrRestoreTextSelection() clears focus from the
WebContents' container view whenever a tab-modal dialog is shown (not
only when text is selected), to dismiss the text selection action bar.
Nothing gave focus back when the dialog closed, so after e.g. a
permission prompt the page stayed blurred until the user tapped it.
Since crrev.com/c/8077560 this also keeps sensors suspended, so
devicemotion and deviceorientation events stop after answering a
permission prompt.

Request focus for the container view when the dialog is dismissed,
mirroring the clearFocus() call. This matches desktop, where the page
regains focus when a permission bubble closes.

ChromeTabModalPresenter only asks for this when the tab is still
interactable and selected, so focus isn't restored when a dialog is
suspended or dismissed because of a tab switch, the tab switcher, or
the tab closing.

This doesn't change the page losing focus while the dialog is showing;
only giving focus back is new.

Investigated and written with the help of Claude Code. I reviewed and
understand the change and tested it manually on a Nothing 3a running
Android 16, in touch mode, with a keyboard (Enter and Escape to dismiss
the prompt), and with a tablet-sized display (switching tabs while a
prompt is showing).
