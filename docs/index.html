[Actor]: Wire ToolRegistry to ToolRequest::GetToolDefinition()

ToolRegistry provides a central catalog of browser tool schemas for
ActorKeyedService (go/actor-tool-registry-design). Separately,
ToolRequestVariant already lists every ToolRequest subclass supported
by the Actor framework.
Right now, ToolRegistry returns an empty list because ToolRequest has
no standard method for subclasses to expose their schemas, leaving the
registry with no way to collect definitions across ToolRequestVariant.
This CL updates ToolRegistry to iterate over ToolRequestVariant and
collect each tool's schema via a new static
ToolRequest::GetToolDefinition() method, and adds completeness tests to
validate registered schemas. The base GetToolDefinition() returns
std::nullopt (and logs NOTIMPLEMENTED()) as a fallback for unmigrated
tools, so the registry remains empty until follow-up CLs implement
GetToolDefinition() on individual ToolRequest subclasses.

OfflineAudioContext incremental rendering

This CL implements incremental rendering support for
OfflineAudioContext.startRendering. These changes reflect the steps of
the current startRendering algorithm of the Web Audio specification:
https://webaudio.github.io/web-audio-api/#dom-offlineaudiocontext-startrendering

These changes are gated by a feature flag so that the old behavior shall
be observed while the flag is disabled. Regression tests have been added
to make sure these observable behaviors still happen while the feature
flag is disabled. While the flag is disabled,
- Passing an OfflineAudioContextOptions dict to the OAC constructor will
  throw a TypeError with the same message that is currently used
- Passing a chunkSize value to startRendering will just set the internal
  value to std::nullopt, which should trigger the old behavior of
  rendering the whole buffer at once.
- Exceptions will be thrown if startRendering is called twice or if
  called while it is suspended.

Make the occlusion tracker's per-window opacity check cheaper

On Windows, NativeWindowOcclusionTrackerWin computes occlusion by
walking every top-level window on the desktop with EnumWindows() and
calling gfx::IsWindowVisibleAndFullyOpaque() on each one. Calculations
are scheduled on a 16 ms timer, so a steady stream of window location
change events, for example from a window that keeps resizing itself, can
cause up to 62 full scans per second.

For windows that pass its first checks, IsWindowVisibleAndFullyOpaque()
paid Win32 and GDI costs that it did not need:

- It called GetWindowPlacement(), a syscall, only to learn whether the
  window is maximized.
- It created a GDI region, had GetWindowRgn() copy the window region
  into it and deleted it again, only to read the region type.
- For tool windows and popups, gfx::GetClassName() heap-allocated and
  zero-filled a MAX_PATH std::wstring. The taskbar, which is both, had
  its class name read twice.

This change gets the same answers more cheaply:

- IsZoomed() replaces GetWindowPlacement(). Minimized windows are
  filtered out earlier in the function, so the two agree, and IsZoomed()
  only reads the window's style.
- GetWindowRgnBox() replaces GetWindowRgn(). It returns the same region
  type without creating a GDI object.
- The class name is read at most once per window, into a stack buffer,
  and compared as a std::wstring_view. RegisterClassEx() rejects class
  names longer than 255 characters, so the buffer holds any class name
  in full.

In a CPU sampling profile of Microsoft Edge, which shares this code,
IsWindowVisibleAndFullyOpaque() took 77% of the occlusion calculation's
samples (82,802 of 107,580). Within the function, GetWindowPlacement()
took 53%, gfx::GetClassName() 27%, and creating and deleting the region
5%. GetWindowPlacement() and the region creation and deletion, which
this change removes, made up 57% of the function's samples, or 44% of
the whole calculation.

In per-call timings taken for the same change in Microsoft Edge,
IsZoomed() took about 5 ns where GetWindowPlacement() took about 440 ns,
and GetWindowRgnBox() about 7 ns where creating a region, calling
GetWindowRgn() and deleting the region took about 300 ns. A window that
reaches both checks therefore costs about 730 ns less per scan. On a
desktop with 1,022 top-level windows, IsZoomed() agreed with
GetWindowPlacement(), and GetWindowRgnBox() with GetWindowRgn(), for
every window.

Tested by new WindowVisibleAndFullyOpaqueTest cases in gfx_unittests for
a window with a simple rectangular region, a maximized window, a popup
tool window of the taskbar's class, and a popup window whose Chrome
widget class name has the maximum length of 255 characters. Existing
tests cover the other filters, including complex regions, tool windows
and popups.

[Actor] Restore unassociated background tabs from pool when live in memory

When background actuation tasks (such as those triggered via Remy /
Spark / Glic) complete without creating placeholder tabs in the
foreground TabModel, the background tabs are registered into
BackgroundTabPool and saved to TabCache. When the foreground service
terminates while Chrome is in the background, the Chrome process remains
alive as a cached Android process, retaining the LiveBackgroundTab
instances in BackgroundTabPool.mLiveEntries.

Previously, BackgroundTabPool.claimTabIdsWithoutPlaceholders()
explicitly excluded tabs in mLiveEntries under the assumption that live
tabs would always be restored by warm Activity restoration. However,
when Chrome is subsequently opened by the user (cold startup of
ChromeTabbedActivity within the existing process),
ActorBackgroundActuationManager is null and no warm sessions remain,
while cold session restoration skipped the tabs because
claimTabIdsWithoutPlaceholders() filtered them out. Consequently, the
tabs were lost until Chrome was force-killed and reopened.

Additionally, BackgroundTabPool.loadTabByOriginalId() failed to handle
LiveBackgroundTab entries (directly calling loadTabInternal, which
asserted against live entries), and
BackgroundTabRestorationHelper.restoreRemainingBackgroundTabs() asserted
that loaded tabs could not be live while omitting prepareForForeground()
for reparenting.

This CL:
1. Updates BackgroundTabPool.claimTabIdsWithoutPlaceholders()
   to include live unassociated tabs instead of stripping mLiveEntries.
2. Updates BackgroundTabPool.loadTabByOriginalId() to return the
   LiveBackgroundTab if present, mirroring loadTabByPlaceholderId().
3. In BackgroundTabRestorationHelper.restoreRemainingBackgroundTabs(),
   removes the assertion against live tabs and calls prepareForForeground() before attaching tabs into the TabModel.
4. Updates unit test coverage in BackgroundTabPoolTest and
   BackgroundTabRestorationHelperTest.

[activity_reporter] Implement Windows VM detection via CPUID and SMBIOS

Replaces the placeholders in virtual_machine_stub_win.cc with the two
real implementations being compared, and flips kVmDetectionExperiment
to enabled by default so that the Windows.VmDetection.* histograms are
recorded. The feature is kept as a kill switch.

The CPUID arm walks the hypervisor leaves at 0x40000000 + 0x100 * n.
CPUID.1:ECX[31] only means "a hypervisor is present", which is also true
of a physical machine running VBS/HVCI, Credential Guard, WSL2 or Windows
Sandbox (all Hyper-V root partitions). So a "Microsoft Hv" signature is
not taken at face value: the root-partition privilege bit is checked,
and later leaves are scanned for a second vendor hiding behind the
Hyper-V facade (VirtualBox, Parallels, QEMU/KVM with enlightenments).
An unrecognized hypervisor is reported as kUnknown and counts as "don't
know" rather than as a VM, since some security products run the
physical host under their own thin hypervisor. On non-x86 CPUs, and for
x86/x64 builds emulated on ARM64, it reports kUnsupportedArchitecture.

The SMBIOS arm parses GetSystemFirmwareTable('RSMB') and matches the
BIOS vendor, system manufacturer and system product strings, falling
back to HKLM\HARDWARE\DESCRIPTION\System\BIOS, and reports kReadFailed
when neither source yields any strings. Hyper-V is matched on the pair
(Microsoft Corporation, Virtual Machine), so physical Surface devices
are not flagged.

The histogram expiry is extended to 2027-06-30 so that the experiment
collects enough stable-channel data to choose between the two
implementations.

[Safe Browsing][iOS] Deflake client-side detection EG tests

Fix two causes of flakiness in `SafeBrowsingTestCase` CSD tests:

1. `testClientSideDetectionRuns`: `PhishingClassifier` posted visual
   feature extraction as `BEST_EFFORT`. At startup, the 2-thread
   `BEST_EFFORT` pool is saturated by disk/DB tasks that run at
   `QOS_CLASS_BACKGROUND` (I/O-throttled on Apple platforms), delaying
   extraction by tens of seconds, past the test timeout. Since
   extraction is cheap (~15-35ms) and its verdict can surface a warning,
   run it at `USER_VISIBLE` (scoring in `scorer.cc` remains
   `BEST_EFFORT`).

2. `testClientSideDetectionForceRequest`: under Enhanced Protection, 1%
   of high-confidence allowlisted loads send a sampled real-time lookup
   ping that bypasses the verdict cache and overwrites the injected
   `FORCE_REQUEST` verdict before classification completes. Switch from
   `_safeURL1` (marked via `--mark_as_allowlisted_for_real_time`) to
   `_safeURL2` so no sampled ping is sent.

Verified with Swarming runs on the ios-simulator coverage config:
- `testClientSideDetectionRuns` passed 5/5 runs with its fix (no retries
  needed) vs 3/11 attempts across 5 runs without its fix, and
- `testClientSideDetectionForceRequest` (with sampling forced to 100%)
  passed 20/20 with its fix vs 7/10 without its fix.

Add a 14-day minimum publish age for chromium_crates_io updates

This change sets `[registry] global-min-publish-age = "14 days"` in
`third_party/rust/chromium_crates_io/.cargo/config.toml`. With this
setting, cargo only uses crate versions that are on crates.io for 14
days or more. This decreases the risk that Chromium receives a malicious
release before crates.io removes it. The bug gives the reasons for the
14-day value.

Before this change, `.cargo/config.toml` told cargo to use the crates in
`vendor/`, and gnrt removed the file while it ran online commands
(`without_cargo_config_toml`). Because of this, cargo could not read a
setting from the file during `gnrt add` or `gnrt update`.

This change moves the `vendor/` source replacement to
`.cargo/offline-config.toml`. Cargo does not read this file
automatically. gnrt gives it to cargo with `--config` for the commands
that must use the vendored crates (`gnrt gen` and the second step of
`gnrt vendor`). `third_party/rust/PRESUBMIT.py` does the same for its
`cargo metadata --offline` check. gnrt does not remove any file now, so
all online commands (`gnrt add`, `gnrt update`, and the first step of
`gnrt vendor`) read the 14-day setting, also when you run them manually.

When an update is necessary immediately (for example, a security fix),
you can disable the 14-day limit for one command. To do this, set
`CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow`.
`tools/crates/create_update_cl.md` gives the procedure.

`chrome/browser/thumbnail/cc/etc1_thumbnail_helper.cc` using

`ui::Etc1::CompressBitmap` and the Rust `decompress_etc1` implementation
in `ui/android/texture_compressor` was not exposed over FFI.

  `ui/android/ui_android_features.{h,cc}` and expose
  `use-new-etc1-decoder` in `chrome://flags`
  (`chrome/browser/about_flags.cc`).

  `ui/android/resources/etc1_utils.{h,cc}` dispatching between Rust
  `decompress_etc1` and `etc1_decode_image` based on
  `kUseNewEtc1Decoder`, and call it from `DecompressTask` in
  `chrome/browser/thumbnail/cc/etc1_thumbnail_helper.cc`.

  `Etc1DecompressBitmapSyntheticBlocksBitExactness`, and
  `Etc1DecompressBitmapInvalidInputs` in

  across POT/NPOT dimensions, all block modes/tables/selectors, and
  guard conditions.

  `testing/variations/fieldtrial_testing_config.json`.

[MagiChrome] Hold Bluetooth adapter on sign-in tab

On macOS, a new BluetoothAdapter reports Bluetooth as off until its
first background poll completes, since that poll moved off the UI
thread. The Chrome sign-in page's WebAuthn request gets a new adapter,
because BluetoothAdapterFactory only keeps a weak reference and nothing
else holds one. The request's transport availability then says Bluetooth
is off, so the inline passkey QR code is missing from Autofill
suggestions shown before the poll completes.

DiceTabHelper now calls IsHybridTransportSupportedForQrCodeSignin() when
a sign-in flow starts, if MagiChrome passkey autofill is enabled, and
holds the adapter while the tab shows the Chrome sign-in page. The
function's callback now also receives the adapter it checked; existing
callers ignore it. The check reads the power state when Bluetooth is
present and permitted, which starts the poll on macOS. The page's
WebAuthn request then reuses this adapter, and the poll can complete
while the page loads. Reusing the adapter also spares the request from
initializing a new one. The adapter is released when the tab leaves the
sign-in page.

ChromeAuthenticatorRequestDelegateTest now reports Bluetooth LE as
unsupported. Its sign-in page tests would otherwise create a real
adapter, which crashes on Linux because unit tests don't initialize
BlueZ D-Bus.

[iOS] Avoid rebuilding identical LocationBarSteadyView constraints

`-[LocationBarSteadyView updateContainerConstraints]` is the sink for
every content update of the steady view: it is called from
`setLocationLabelText:clipTail:` and `setLocationLabelPlaceholderText:`,
which `LocationBarSteadyViewMediator` invokes on navigation start/finish,
loading start/stop, page load, visible security state and title changes.
With ChromeNextIa, this happens for each of the 2 (4 with the glass
toolbar) `LocationBarViewController` instances receiving the same
WebState events.

On every call, the method unconditionally deactivated the previous
container constraints, re-added already attached subviews (which UIKit
treats as a remove and insert) and activated a freshly allocated,
byte-for-byte identical constraint set. This forces a redundant Auto
Layout invalidation of the toolbar subtree several times per navigation
even though the URL text never changes the constraint set.

Cache the inputs the constraint set depends on (incognito badge,
location image, custom leading view presence and spacing) and return
early when they are unchanged, still notifying the content size
delegate. The cache is reset when the custom leading view container is
recreated, as the cached constraints reference the previous instance.

Add unit tests covering constraint reuse on text updates and rebuilds
when the location image or custom leading view changes.

In ProxyProvisioningDomains policy, extra_headers entries specify "key"
and "value" without a "type" field. After crrev.com/c/8116344,
ResolveExtraHeadersWithValues only expands placeholders for
HeaderType::kVariable, causing policy headers containing placeholders

ParseExtraHeadersList defaulted entries without "type" to
HeaderType::kConstant.

Update ParseExtraHeadersList so that "value" entries without an explicit
"type" field are classified as HeaderType::kVariable when they contain
"${", while preserving existing handling for PvD payload

EnsureBig5EncodeTable() and EnsureBig5EncodeIndexForEncode() declared
function-local static instances of Big5EncodeTable and Big5EncodeIndex
by value:

  static const Big5EncodeIndex table = [] { ... }();

Because their initializers are non-constexpr lambdas, both objects
occupied 231.8 KiB in the zero-initialized .bss portion of chrome.dll's
.data section. On Windows, the loader reserves private commit charge
(PMF) for the full VirtualSize of every writable PE section in every
process that maps chrome.dll, even when no Big5 text is ever decoded or
encoded. In practice, non-renderer processes never use these tables, and
even in renderers Big5 not prevalent:
https://en.wikipedia.org/wiki/Popularity_of_text_encodings
Big5 is also considered a "Legacy" encoding:
https://encoding.spec.whatwg.org/#big5


Fix this by heap-allocating Big5EncodeTable and Big5EncodeIndex via
`new` inside the function-local static pointer initializer, matching the
pattern used by the other CJK tables in encoding_tables.cc.

- .data VirtualSize delta: -231.81 KiB (from static analysis)
- Per-process PMF delta: ~ -232 KiB (from real test with

When a user deletes an individual history entry on chrome://history,
BrowsingHistoryService::RemoveVisits() expires visits using a full-day
time_range() restricted to the deleted entry's URLs via restrict_urls(),
while populating deleted_visit_ids() with the exact visit IDs that were
removed.

DeleteCriticalActionsInTimeRange() whenever time_range().IsValid() is
true and returns early, wiping all critical actions recorded on that
calendar day across all URLs and visits.

This CL updates OnHistoryDeletions() to:
 - Only call DeleteCriticalActionsInTimeRange() for partial time-range
   deletions when restrict_urls() is unset (e.g., Clear Browsing Data).
 - Fall through to DeleteCriticalActionsByVisitIds() whenever
   deleted_visit_ids() is non-empty, both to handle URL-restricted
   deletions and to clean up actions whose timestamp fell outside an
   unrestricted time_range().
 - Add unit tests covering URL-restricted deletions and combined
   time-range/visit-ID deletions.
