[Autofill] Preserve BAM popup vector index in FormSuggestionMetadata

Follows the approach used on Android.

BrowserAutofillManager (BAM) expects DidAcceptSuggestion() to receive
the index corresponding to its original suggestion vector rather than
the UI array index. On iOS, AutofillAgent may reorder or filter
suggestions before rendering them (e.g. prepending SuggestionType::kUndo
to the front of the Keyboard Accessory suggestion list).

Passing the UI array index when suggestions are reordered caused an
off-by-one contract mismatch, shifting accepted suggestion indices in:
1. UKM FormInteractionsUkmLogger::LogSuggestionAccepted (corrupting
logged suggestion rows). 2. UMA Autofill.SuggestionAcceptedIndex.*
metrics (corrupting acceptance ranking telemetry).

This CL adds `popup_suggestion_index` to `FormSuggestionMetadata` to
store the original BAM suggestion vector index upon receiving
suggestions in `showAutofillPopup:`, and passes it to
`DidAcceptSuggestion()` when selected.

[chromecast] Embed APK version as Product Version in Crashpad

This modifies the Cast crash reporter client to explicitly set the
Crashpad product_info->version to the APK package version name
(e.g. 3.74.x) instead of the Chromium release string. To ensure
ApkInfo.getPackageVersionName() returns the host APK version rather than
falling back to VersionInfo.getProductVersion(), this also calls
ApkInfo.setBrowserPackageInfo(packageInfo) in
CastBrowserApplication.initialize().

This allows the crash backend to seamlessly cluster native Crashpad
dumps alongside Java exception logs (which already use the APK version).
The original Chromium release string is preserved via a new
browser_version crash key.

Additionally, we now explicitly override the ptype crash key for the
core process vs the sandboxed browser process on Android, separating
cast_service from cast_browser in crash reports since both natively
initialize Crashpad as ptype: browser.

Mac: Activate the widget when focusing a View in an inactive widget

FocusManager::SetFocusedViewWithReason() activates an inactive widget
before focusing a View in it, so that focus implies activation. This was
added in 2016 (codereview.chromium.org/2371113003), but Mac was excluded
only because some AccessiblePaneViewTests failed there, with a TODO
pointing at crbug.com/40486728. As a result, on Mac a View can have
focus in a window that isn't key, so keystrokes keep going to another
window (e.g. a tab-modal dialog). Various Mac-only workarounds have
accumulated for this, such as ActivateWindowAfterFocusCommand() in
browser_commands.cc.

This CL removes the Mac exclusion, behind the kill switch
kMacActivateWidgetOnFocusRequest (enabled by default):

- NativeWidgetPrivate::ShouldActivateOnFocusRequest() lets the platform
  decide whether to activate. It returns true by default, keeping the
  existing behavior on other platforms.
- On Mac, it returns true only when activation is synchronous and has no
  side effects beyond making the window key: the window is in-process,
  visible, can become key, and the app is already active. This avoids
  showing hidden windows, stealing focus from other apps, and async
  activation of out-of-process (app shim) windows. Otherwise, the View
  is focused without activating, as before.
- NativeWidgetMacNSWindowHost::OnIsFirstResponderChanged() no longer
  restores the focused View when the window isn't key. Such a first
  responder change is programmatic (e.g. ClearNativeFocus() during a
  tab switch), and restoring focus would now activate the window. Focus
  is restored when the window becomes key.
- ActivateWindowAfterFocusCommand() in browser_commands.cc is skipped;
  focus commands now activate the browser window through FocusManager.
- ToastController's Mac-only OnWidgetActivationChanged() workarounds
  (clearing the toast's stored focus view on activation and the
  browser's focus on deactivation) are skipped. They compensated for
  focus being set before activation; with activation now going through
  the stored focus view, clearing it left the toast with no focus.
- BrowserView::OnActiveTabChanged() now only restores focus on a tab
  change if the widget is active, as on other platforms. The Mac-only
  exception (crbug.com/926492) relied on restoring focus not activating
  the widget. Otherwise a tab change in an inactive browser, e.g. when
  attaching a dragged tab, would synchronously activate it. Focus is
  restored on activation instead (restore_focus_on_activation_).

The skipped workarounds are kept so that disabling the kill switch
restores the previous behavior. They can be removed together with the
kill switch.

idle-detection: Sever idle monitors upon permission revocation

When a user revokes the IDLE_DETECTION permission in site settings,
IdleManagerImpl continues delivering user idle and screen lock state
updates to existing documents. This happens because IdleManagerImpl
only checks permission at monitor registration and does not subscribe
to permission changes via PermissionController.

This CL subscribes IdleManagerImpl to permission status changes using
PermissionController::SubscribeToPermissionResultChange while any
monitor is registered. When permission is revoked, all active monitor
pipes are dropped, polling is stopped and the subscription is released.

bluetooth: Clean up active notify sessions on ForgetDevice

WebBluetoothServiceImpl::ForgetDevice() revoked device access on the
legacy permissions backend by removing the device address from
allowed_devices(). However, it did not tear down active GATT notify
sessions, pending connection requests, or watch advertisement clients
associated with the forgotten device. If the physical connection was
kept open by another frame or origin, BLE characteristic notification
events continued to be dispatched to the renderer.

This CL introduces CleanupDeviceState() and invokes it during
ForgetDevice() when running on the legacy permissions backend. It closes
the GATT connection, cancels pending connection attempts, removes watch
advertisement clients, and drains in-flight and deferred notify session
requests with GATT_NOT_AUTHORIZED.

[base/i18n] Bind DateTimeFormatter instances to a locale

DateTimeFormatter now receives the locale in its constructor and uses it
to format when no explicit locale is passed to Format().

IcuBridge owns one formatter per locale, cached in an
absl::flat_hash_map keyed by LanguageTag, and exposes:
  - date_time_formatter(): returns the formatter for the current default
    ICU locale, obtained from GetDefaultIcuLocale().
  - date_time_formatter(locale): returns the formatter for the given
    locale.

Formatters are created on first use. The map is lazily populated by the
const accessors and guarded by a lock, as IcuBridge is a process-wide
singleton that can be accessed from any thread.

This change is being done so a cache can be more conveniently
implemented for improving the performance of DateTimeFormatter.

[Crubit] Parallelize Crubit actions via metadata groups

Previously, `cc_bindings_from_rs` (Crubit) actions had a build-time
dependency on `_rspgen_target_name` (`generated_file`), which in turn
depended on `_original_attributes.deps` (e.g. `//build/rust/std:std_bindings`).
Because `std_bindings` and its constituent targets depend on upstream
Crubit header generation actions, this caused GN to emit Ninja hard
dependencies serializing all Crubit actions (e.g. `signed_web_bundles`
behind `std_bindings`, `std_bindings` behind `alloc_bindings`).

`cc_bindings_from_rs` only needs the GN metadata (header path strings,
namespaces, and features) written into the `.rsp` file at `gn gen` time.
It does not consume the generated C++ header files at runtime.

This CL introduces a pure metadata target `_metadata_target_name`
(`${target_name}_crubit_metadata`) including `std_bindings_crubit_metadata`
that contains only GN metadata without any action or library dependencies.
`_rspgen_target_name` depends on these metadata targets instead of the
action-bearing targets, and `_action_target_name` explicitly lists
`_action_rsp_path` in its `inputs` and depends on `_rspgen_target_name`.

This:
1. Breaks the Ninja harddeps chain between Crubit actions, allowing
   all Crubit actions to run fully concurrently as soon as their Rust
   libraries build.
2. Ensures `_action_rsp_path` is explicitly declared in `inputs` so
   remote execution (RBE) workers receive the `.rsp` file.
3. Preserves `_original_attributes.deps` on `source_set(_h_target_name)`
   so that downstream C++ compilations still wait for generated headers.

gamepad: Support Switch Pro 48-byte Bluetooth input reports

Nintendo Switch Pro Controllers and Joy-Cons connected over Bluetooth
transmit 49-byte HID transfers (1-byte report ID + 48-byte report body)
for standard input reports (0x30) and SPI subcommand replies (0x21),
whereas USB connections transfer 64 bytes (1-byte ID + 63-byte body).

Previously, crrev.com/c/7694899 introduced input report size checks
validating reports against 63-byte USB structures (ControllerDataReport
and SpiReadReport). On Linux, where hidraw delivers exact Bluetooth
packet sizes rather than Windows HID subsystem-padded reports, this
caused all incoming Bluetooth reports to be rejected, breaking device
initialization and gamepad input polling.

This CL resolves the issue by:
1. Defining ControllerDataReportBluetooth (48 bytes) and
   SpiReadReportHeader (19 bytes) packed structs to model the Bluetooth
   report layout.
2. Checking bus_type_ to dynamically validate 48-byte minimum sizes on
   Bluetooth and 63-byte sizes on USB in HandleInputReport30,
   HandleInputReport21, and ContinueInitSequence.
3. Updating touched report handler lines from UNSAFE_TODO to
   UNSAFE_BUFFERS with explicit // SAFETY: comments documenting size
   invariants.
4. Updating SPI read unpacking to accept base::span<const uint8_t> with
   defensive bounds checking against the actual payload size.
