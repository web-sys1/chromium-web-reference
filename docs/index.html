[iOS] Fix PageContextWrapperTest.PopulatePageContextWithShadowDom on iOS 27

Wait-free innerText extraction in getInnerTextIncludingShadowDom()
appends open shadow root text chunks after the host node's light-DOM
innerText using '\n' as the separator. However, node.innerText was not
trimmed before joining (unlike direct text node children of a shadow
root, which are trimmed).

On iOS < 27 WebKit, reading document.body.innerText when a <p> element
is followed by shadow host <div> elements without rendered light-DOM
text emitted two trailing newlines ("light-dom text\n\n"), producing
three newlines when joined with the first shadow text chunk. On iOS 27
WebKit, trailing newlines after <p> are no longer emitted when
subsequent siblings produce no light-DOM text, causing
PopulatePageContextWithShadowDom to fail.

Trim node.innerText in getInnerTextIncludingShadowDom() so light-DOM
and shadow-DOM text chunks are consistently separated by a single
newline across iOS versions, and re-enable
PageContextWrapperTest.PopulatePageContextWithShadowDom.

[BottomBar] Defer the NTP theme tip once bottom bar education has shown

The NTP theme tip bottom sheet can open on top of bottom bar education;
for example, a new tab opened from the tour's "+" step shows the sheet
over the tour. The tip isn't an IPH, so Feature Engagement doesn't hold
it back.

Keep an in-memory flag in BottomBarEducationCoordinator, set when the
bubble, the tooltip tour or the opt-in dialog shows, and skip the theme
tip in NewTabPageCoordinator while it's set. The flag lives as long as
the process, so it survives the activity recreate from "Try it now" and
resets when the process restarts. The tip is only marked as shown when
it actually shows, so it's deferred, not dropped.

cros: Fast-shutdown renderers and skip window hide animation on exit

On ChromeOS, ExitIgnoreUnloadHandlers() handles SIGTERM from
session_manager and passes ShutdownType::kBrowserExit when all
browsers are closeable or ShutdownType::kEndSession otherwise. Add
browser_shutdown::ShouldFastShutdownRenderers() returning true on
ChromeOS for ShouldIgnoreUnloadHandlers() and kBrowserExit, and pass
it as skip_unload_handlers, ignore_workers, ignore_keep_alive, and
ignore_pending_reuse to RenderProcessHost::FastShutdownIfPossible() in
OnShutdownStarting() and TabStripModel::CloseWebContentses().

With ignore_workers and ignore_keep_alive enabled on ChromeOS,
renderer processes running service workers or pending fetch(keepalive)
requests are terminated immediately when shutdown starts to stay
within the 3 s session_manager budget; session restore state lives in
the browser-side NavigationController and is unaffected. Also disable
visibility-change animations on the browser widget on ChromeOS in
BrowserView::Close() once shutdown has started so
wm::WindowAnimations does not clone the window layer tree during
process exit.

SiteIsolation: Add shards for default SiteInstances

Allows an embedder to split sites that don't need a dedicated process
into "shards". Sites in different shards never share a renderer
process, while sites within a shard can still share one. This is
intended for Android WebView, which doesn't use full Site Isolation, so
that a set of sites can be kept out of the renderer used for all other
web content without giving each site its own process (known as WebView
Site Sharding).

Each BrowsingInstance has one default SiteInstance per shard. They all
use the same default site URL, and are distinguished by the shard on
their SiteInfo (SiteInfo::shard()). Shards are only supported with
default SiteInstances, not yet default SiteInstanceGroups (which WebView
doesn't use), and this is CHECKed.

ProcessLock records the shard of each process that is not locked to a
site. The shard is assigned when an allows-any-site process is first
used, after that it can't change so ProcessLocks for different shards
never compare equal. RenderProcessHostImpl::IsSuitableHost() and
ChildProcessSecurityPolicy compare the process's ProcessLock shard
against the destination SiteInfo's shard. Shards only divide up sites
that don't need a dedicated process.

//content:
- SiteShard (content/browser/site_shard.h) is an enum with two values:
  kDefault, for all sites that aren't specified by the embedder, and
  kEmbedderSites.
- BrowserContext::SetSitesForEmbedderShard(sites) puts a set of sites
  (net::SchemefulSite) in the embedder shard. It can only be called
  once, before any RenderProcessHost in the BrowserContext is used, and
  CHECKs that sites are HTTP(S) and that default SiteInstanceGroups,
  single-process mode and the Rust ChildProcessSecurityPolicy
  ProcessState aren't in use. This could be extended to multiple shards
  if needed.
- SiteInfo::shard() is computed in SiteInfo::Create() from the origin
  that will be committed (so data: URLs use their initiator's shard and
  LoadDataWithBaseURL uses the base URL's) and is part of SiteInfo
  equality and ProcessLock comparisons. This is skipped when the
  BrowserContext has no shards.
- BrowsingInstance keeps one default SiteInstance per shard.
- ProcessLock::shard() is assigned when an allows-any-site process is
  first used (ChildProcessSecurityPolicyImpl::SetProcessIsUsed(), via
  ProcessLock::SetIsUsed()); changing it is a CHECK failure.
  RenderProcessHostImpl::IsSuitableHost() won't reuse a process across
  shards, and the Citadel checks ensure processes only host content
  from their own shard.
- When shards are configured, error pages for blocked renderer-initiated
  requests commit in the destination's process rather than the current
  one (NavigationRequest::ComputeErrorPageProcess()), so a process never
  ends up hosting content from another shard.

//android_webview:
- AwBrowserContext::SetSitesForEmbedderShard() puts the given sites in
  the embedder shard and CHECKs it isn't in single-process mode. Nothing
  calls it yet; the API plumbing will follow separately.

[SafeBrowsing] Prioritize navigation database lookup callbacks

While `NavigationURLLoader` processes network responses on
`BrowserTaskType::kNavigationNetworkResponse`, SafeBrowsing checks are
initiated during `WillStartRequest` on the default normal-priority UI
task queue (`QueueType::kDefault`). Because
`SBDatabase::GetStoresMatchingFullHash` used
`PostTaskAndReplyWithResult`, lookup replies were bound to
`GetCurrentDefault()` (`kDefault`). When the browser UI thread default
queue is congested, a navigation deferred in `WillProcessResponse`
waiting on `sync_sb_checker_` is delayed behind normal-priority UI
tasks. Under
`safe_browsing::kPrioritizeSafeBrowsingNavigationCallbacks`:
- Sets `prioritize_navigation_callbacks` on `UrlCheckerHolder` in
  `BrowserURLLoaderThrottle::WillStartRequest` (so
  `UrlCheckerHolder::Start` passes
  `BrowserTaskType::kNavigationNetworkResponse` to
  `SafeBrowsingUrlCheckerImpl`) only for non-prefetch navigation checks
  that perform synchronous hash-database lookups (including
  `sync_sb_checker_` when `AsyncCheckTracker` is enabled), keeping
  `async_sb_checker_`, real-time checks, and prefetch requests on the
  default UI queue.
- Plumbs the checker's callback task runner through
  `DatabaseManagerMechanism` (`Client::GetCustomCallbackTaskRunner()`)
  to `SBDatabase::GetStoresMatchingFullHash` so only synchronous
  navigation database checks post lookup replies onto
  `kNavigationNetworkResponse`. Android's
  `RemoteSafeBrowsingDatabaseManager` is handled in a follow-up CL.

[Android] Filter side panel tests on phone CQ

Side panel does not exist on Android phones, so
SidePanelAndroidBrowserTestBase::SetUp() unconditionally calls
GTEST_SKIP() on phone form factors. However, because
android_browsertests spawns a fresh ChromeBrowserTestsActivity process
for every test case, all 95 tests in
SidePanelCoordinatorAndroidBrowserTest and
SidePanelRegistryAndroidBrowserTest still pay Java Activity startup and
library load overhead (~1.3 s per test) just to skip in 1-2 ms. These
suites cannot be compiled out of non-desktop Android builds because
tablet bots share the non-desktop build and run them.

Add android.phone.android_browsertests.filter excluding both suites as a
host-side performance optimization and wire it on the CI builders
mirrored by the phone CQ bots (android-x64-rel, android-x86-rel, and
android-arm64-rel). On android-x64-rel (25 shards), this eliminates 95
no-op Activity launches per android_browsertests run (~120 s cumulative
process launch overhead across shards, or ~5 s per shard).

[Android] Match InProcessBrowserTest feature list

Previously, AndroidBrowserTest left default search engine preconnect
(kPreconnectToSearch, which fires with a 0 ms startup delay on Android),
search engine prewarm (kPrewarm, which warms up a background prerender
renderer and compositor during startup),
kRestartNetworkServiceUnsandboxedForFailedLaunch,
kTransientKeepAlivePolicy, and in-product help features enabled, unlike
desktop's InProcessBrowserTest.

Disable these background features by default and block IPH via
ScopedIphFeatureList in AndroidBrowserTest to match
InProcessBrowserTest, avoiding unnecessary startup overhead and
nondeterministic background work. Dedicated tests for these features can
still enable them via ScopedFeatureList or ScopedIphFeatureList.

Measured impact: On a 5-test local android_browsertests batch (5 runs on
emulator-5554), batch wall time drops from 17.24 s to 16.66 s (-3.4%, or
-118 ms/test) in default run-from-apk mode and from 15.41 s to 14.86 s
(-3.5%, or -108 ms/test) after package compilation, with mean GTest
runtime dropping by 4.4% to 5.2%.

Fix priority queuing when replacing infobars

Prevent an infobar replacement from incorrectly remaining visible when
it is outranked by a queued infobar. This scenario occurs when a visible
high-priority (e.g., Default) infobar is replaced by a lower-priority
(e.g., Low) infobar while another high-priority infobar is already
queued.

To fix this, extract the admission logic into a CanAdmit helper and
evaluate the replacement's eligibility before allowing it to occupy the
visible slot. If the replacement is outranked by any queued infobars,
queue the replacement instead, clean up the old infobar's visible state,
and promote the highest-priority queued infobar.

Additionally, defer queued-count pill updates during replacement to
avoid recording redundant metrics. The update is deferred using a
boolean flag while OnInfoBarReplaced runs. When the replacement settles,
the pill is moved to its new host without registering a new "Shown"
sample, preserving the accuracy of the pending indicator metrics and the
host resolve time.

[GEiC] Use the GEiC FRE instead of the consumer FRE for consent

Adds a per-provider FRE store so that GEiC profiles use the GEiC FRE for
GLiC consent instead of the consumer FRE:

- New `GlicFreStore` interface with Gemini and GEiC implementations
  (status read/write, onboarding completion, developer switches,
  sign-out handling). Each profile's `GlicProviderSpec`, latched by
  `GlicProviderLatch`, owns its store and returns it from
  `GetFreStore()`: the GEiC store for GEiC profiles, else the Gemini
  store.
- `GlicEnabling::GetCompletedFre()`, `SetCompletedFre()` and Android
  sign-out go through the store. The GEiC FRE can only be completed,
  not dismissed, and isn't reset on sign-out (it's stored per GE
  instance, not per account).
- `GlicEnabling` observes only the active store's status pref
  (`GlicFreStore::GetStatusPrefName()`), so changes to the other
  provider's FRE don't notify consent observers.
- `GlicKeyedService` applies the store's developer switches, replacing
  the consumer switch handling and geic_init. Consumer FRE switches
  don't apply to GEiC; use `--geic-reset-fre` / `--geic-always-skip-fre`.
- `SetOnboardingCompleted()` calls the store's `CompleteOnboarding()`:
  the Gemini store keeps the consumer side effects (metrics, OS
  launcher, IPH), the GEiC store only records completion. The consumer
  side effects are moved unchanged, including the `FindTabbedBrowser()`
  lookup for the IPH event that the banned-pattern presubmit flags.
- With `kGeicFre`, the GEiC settings section stays hidden until the
  GEiC FRE is completed (`GlicFreStore::HidesSettingsUntilCompleted()`).
- New `GlicProviderSpec::SupportsAnchoredEntryPoint()`: only consent
  for providers that support it anchors the entry point
  (`kGlicAnchorEntryPointForOnboardedUsers`). GEiC doesn't for now,
  since the anchored error state shows Gemini (consumer) copy and help
  links (b:576834093). A GEiC profile that fails a Glic requirement has
  no entry point, like a profile that hasn't onboarded.

The GE web app keeps using the existing onboarding API.

`GlicEnabling` gets the store from `GetGlicProviderSpec(profile)`, so the
FRE follows the provider that `GlicProviderLatch` resolved when the
profile was created (b:574499029). The GEiC FRE applies only to
profiles latched to Gemini Enterprise.

Without `kGeicFre` (until the GE web app can complete the GEiC FRE),
GEiC profiles are always consented instead of falling back to the
consumer FRE, and never read or write the consumer FRE or apply its
developer switches. Provider gating of GiC features for GEiC will
follow.

[layout] Add flag to skip the forced initial scrollbar.

Today when we have layout affecting scrollbars, we always add vertical
scrollbar on the initial layout.

This reasoning for this is that if we had a lot of content we'd layout
at the correct size, but if we didn't have a lot of content it'd be
cheap to remove the scrollbar.

This probably made sense when more of the web was "content" based, e.g.
articles etc. However today with SPAs etc, typically no scrollbar is
needed on the initial, and removing the inital scrollbar isn't
nessecerily cheap.

This code was added in:
https://chromium.googlesource.com/chromium/src/+/06ad6bbbc8b17

Lets run an experiment to disable this logic and see if it has an effect
on FCP/LCP.

Additionally this make the initial render more stable.

[gtk] Skip redundant dark-theme updates in GtkUi::SetDarkTheme()

During browser startup on Linux, PortalSettingsLinux reads the desktop
color-scheme preference over D-Bus and calls LinuxUiTheme::SetDarkTheme
once the reply arrives (right after entering the main message loop).

Unlike OsSettingsProviderGtk::SetColorScheme(), GtkUi::SetDarkTheme()
unconditionally called g_object_set() on
gtk-application-prefer-dark-theme even when PreferDarkTheme() already
matched the requested value (such as false in the default light theme,
or true when dark mode is already configured in GTK settings). In
GObject/GTK3, setting this property unconditionally resets GTK CSS
style values and emits notify::gtk-application-prefer-dark-theme,
triggering GtkUi::OnThemeChanged(), rebuilding all GTK color maps,
broadcasting NativeTheme::NotifyOnNativeThemeUpdated() across all
Views, and invalidating chrome://theme/colors.css mid-startup.

Skip calling g_object_set() when PreferDarkTheme() == dark. Genuine
light/dark transitions continue to update GTK settings and notify theme
observers as before. Also restore LC_NUMERIC to "C" after
GtkInitCheck() in run_all_unittests.cc to preserve base::TestSuite's
locale invariant when tests call GtkUi::Initialize().

Crossbench browser-startup results on Linux (--separate --repeat=32
across newtab_startup, blank_startup, and google_startup; 384 runs):
- Default flags (n = 96 paired runs):
  - InitialWebUI.Startup.ReloadButton.FirstContentfulPaint:
    812.2 ms -> 745.5 ms (-66.7 ms / -8.2%, p = 3.2e-26;
    newtab: -77.5 ms / -9.5%, blank: -57.7 ms / -7.2%,
    google: -65.0 ms / -8.0%), cutting the post-window-paint blank
    reload-button gap by 41.1% (161.7 ms -> 95.2 ms).
  - Startup.BrowserMessageLoopFirstIdle:
    824.4 ms -> 760.2 ms (-64.2 ms / -7.8%, p = 7.2e-12).
  - Startup.BrowserWindow.FirstPaint (650.5 -> 650.3 ms) and
    Startup.FirstWebContents.NonEmptyPaint3 (861.6 -> 865.5 ms):
    neutral (p = 0.95, p = 0.46).
- Explicit browser.config.hjson initial_webui flags (n = 96 runs):
  - InitialWebUI.Startup.ReloadButton.FirstContentfulPaint:
    897.7 ms -> 844.5 ms (-53.2 ms / -5.9%, p = 1.1e-11).

uninitialized-memory read when reporting a model load failure on an

a result, loading an invalid model no longer reads uninitialized
memory.

unconditionally. As a result, the test no longer depends on
process-wide static feature initialization and passes reliably.
