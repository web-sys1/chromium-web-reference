Return EditContext selection bounds from TextInputManager::GetSelectionRegion

TextInputManager::GetSelectionRegion() and OnSelectionBoundsChanged()
only consider the DOM selection reported via SelectionBoundsChanged.
For EditContext-based editors (e.g. Google Docs), the DOM selection
often lives in a hidden element (Docs parks it in an iframe at
top:-10000px), while the rendered caret/selection bounds are supplied
by the page via EditContext.updateSelectionBounds() and arrive in
TextInputState::edit_context_selection_bounds. As a result, callers of
GetSelectionRegion() and OnSelectionBoundsChanged() (such as
WebContents::GetFocusSelectionBounds(), GetTextSelectionBounds(), and
RegisterFocusSelectionBoundsChanged(), used by the Dictation / Voice
Typing overlay) see stale or off-screen bounds in EditContext editors.

This change:
- Tracks a parallel ViewMap<std::optional<SelectionRegion>>
  edit_context_selection_region_map_ in TextInputManager, updated in
  UpdateTextInputState() from non-empty EditContext selection bounds and
  returned from GetSelectionRegion() before falling back to
  selection_region_map_, so DOM selection updates do not overwrite
  EditContext bounds and vice versa.
- Notifies OnSelectionBoundsChanged() observers when the active view's
  EditContext SelectionRegion changes.

[iOS] Move snapshot downsampling off the main thread

Snapshot downsampling currently uses UIGraphicsImageRenderer
synchronously from SnapshotStorage::setImage, which can block the UI
thread while rasterizing large tab snapshots.

Move downsampling into the serial background queues already used by
the Swift and legacy image file managers. Keep setImage synchronous by
caching the original image immediately, then replace it with the
optimized image on the main thread after the background write finishes.
Track per-snapshot write generations so stale callbacks cannot overwrite
newer images or restore removed snapshots.

Add coverage for the asynchronous downsampling result, callback
sequence, point size, scale, and pixel dimensions.

Fix race in CancelFlowOnAccountRemoval browser test

In
ProfileManagementDisclaimerServiceBrowserTest.CancelFlowOnAccountRemoval,
a RunLoop::RunUntilIdle() runs after creating the profile management
disclaimer dialog before
handler->SetJavaScriptAllowedCallbackForTesting() is registered. If the
WebUI page finishes initializing during that RunLoop, AllowJavascript()
has already been called on ManagedUserProfileNoticeHandler before the
test registers its callback. Because
WebUIMessageHandler::AllowJavascript() only invokes
OnJavascriptAllowed() on the transition to allowed, the callback is
never invoked and javascript_allowed_future.Wait() times out.

Update
ManagedUserProfileNoticeHandler::SetJavaScriptAllowedCallbackForTesting
to invoke the callback immediately if IsJavascriptAllowed() is already
true.
