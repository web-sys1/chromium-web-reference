[a11y] Don't record reverse relations to an invalid node ID

AXTree::UpdateReverseRelations() inserted the source node into
int_reverse_relations_ under the new target ID even when that ID was
kInvalidAXNodeID. This happens whenever aria-activedescendant is cleared
and whenever a node that had it is destroyed, since destruction updates
the node's relations to empty data. Nothing removes entries keyed by
kInvalidAXNodeID, so the map kept growing with the IDs of cleared and
deleted nodes for the lifetime of the tree.

Skip the insertion for kInvalidAXNodeID, matching the int list relation
handling just below, and add a test that churns relation sources.

[omnibox] Lazily load OmniboxPedalProvider concept data on first match

When BrowserView creates LocationBarView and OmniboxController during
browser window initialization, ChromeAutocompleteProviderClient eagerly
constructs OmniboxPedalProvider, which calls LoadPedalConcepts() to
decompress, tokenize, case-fold, and sort localized synonym groups for
all ~40 omnibox pedals. In browser_tests (and browser sessions where the
user never types in the omnibox), this work is never used, accounting
for ~0.8-1.0% of total browser_tests CPU time (~35-50 ms CPU per test).

Defer LoadPedalConcepts() until the first call to FindPedalMatch(),
while keeping the incomplete-label filtering in the constructor.

[content_settings] Skip ScopedDictionaryPrefUpdate when pref dict is empty

During profile initialization, PrefProvider constructs ~100
ContentSettingsPref instances (one per ContentSettingsType), each
calling ReadContentSettingsFromPref(). Even when the underlying pref
dictionary is empty (the common case for almost all content settings
types), ReadContentSettingsFromPref() unconditionally allocates a
ScopedDictionaryPrefUpdate and calls update->Get(), which clones the
default dictionary into the mutable user pref store and triggers
ScopedDictionaryPrefUpdate teardown. Across multiple profiles initialized
in browser_tests, this accounts for ~0.5-0.7% of total CPU time
(~25-35 ms CPU per test).

Return early from ReadContentSettingsFromPref() after clearing
value_map_ when prefs_->GetDict(pref_name_).empty() is true.

blink::AudioArray wraps a PartitionAlloc-backed base::HeapArray, but its
user-declared deleted copy operations implicitly suppressed move
construction and move assignment. Because AudioArray was non-movable,
callers across platform/audio and modules/webaudio wrapped
AudioFloatArray in std::unique_ptr to return kernels from helper
functions, pass ownership into DirectConvolver, store per-channel
buffers in Vector, or lazily allocate buffers in AudioChannel and
WaveShaperKernel.

and store AudioFloatArray by value across AudioChannel, DirectConvolver,
UpSampler, DownSampler, ReverbConvolverStage, DynamicsCompressor, and
WaveShaperKernel to eliminate redundant heap allocations and pointer
indirections.

[loomnibox] Keep WebContents alive when closing with a modal open

OmniboxEverywhereUIManager::Close() calls CleanUpWidget() when a modal
dialog (e.g. the Drive picker) is open, which destroyed the widget and
also synchronously destroyed the WebUIContentsWrapper and its
WebContents. Close() is reachable from inside calls on that same
WebContents, e.g. WebContentsImpl::OpenURL -> OpenURLFromTab ->
OmniboxEverywhereService::OpenUrl -> HidePopup -> Close(), so
unwinding back into WebContentsImpl/RenderFrameHostImpl resulted in a
use-after-free. The faulty assumption was that closing the popup
requires destroying its contents; that dates from when Close() always
destroyed the widget, before the contents were preserved across
invocations.

Rename CleanUpWidget() to DestroyWidgetAndWebContents() and split out
DestroyWidget(), which tears down the widget and the UI it owns
(dialogs, menus, overlays) and resets transient UI state while keeping
the WebContents. Close() now only calls DestroyWidget() when a modal
is open: destroying the widget still closes the dialogs it owns,
including native ones that can't be dismissed directly, while the
WebContents stays alive and is reused by the next widget.
DestroyWidgetAndWebContents() remains for Shutdown(), the destructor,
and other callers that can't run on the contents' stack.

Filter download URLs for supervised users

Checks the download's URL chain (including redirects) against the
supervised user URL filter in DownloadTargetDeterminer, gated by the
kFilterDownloadUrls feature (enabled by default). If any URL in the

CDN hosts) from bypassing supervised user URL filtering.

[Autofill] Let the renderer agent reject form-change notifications by type

ChromeClientImpl::DidChangeFormRelatedElementDynamically() is called for
every form-related element inserted into or removed from the document
and constructs a WebElement (a cppgc::Persistent) to hand to
WebAutofillClient, whose AutofillAgent implementation then discards most
of them: before DOMContentLoaded, removals without an observer, and any
control type Autofill does not fill (checkboxes, radio buttons, buttons,
...). On pages that churn many small form controls this is a measurable
part of DOM insertion/removal.

Pass WebAutofillClient::DidChangeFormRelatedElementDynamically() the
change type and the element's FormControlTypeForAutofill() up front, and
the element itself as a base::FunctionRef<WebElement()> that is only
invoked when the client wants it. AutofillAgent now runs its cheap
early-outs first and shares the control-type relevance check via a
GetAutofillFormControlType(FormControlType) overload. Behaviour is
unchanged: every notification that previously reached form extraction
still does.

Speedometer 3.1 on a Linux x64 official (ThinLTO+PGO) build, 40 paired
runs: about +0.1% on top of the Blink-side insertion/removal trims, with
TodoMVC-jQuery (which creates and destroys a checkbox and a text field
per item) a further 1.2% faster in wall time.

[masonry] Track alignment space per item

Before this change, the stacking-axis alignment iterator called
`GetAvailableAlignmentSpaceForItem()` once for each item above an
opening. For each lane that the item spans, that function scanned the
lane's openings from the start until it found the item. If N track
openings are spread evenly across L lanes, each lookup is O(N/L), and
the total cost is O(N^2/L) (when openings are evenly distributed across
lanes). This is still quadratic for a fixed number of lanes. In the
worst case, where most openings are in one lane, the total cost is
O(N^2).

After this change, each item's alignment candidates share one
`AlignmentSpace`, which is updated while the track openings change. It
keeps the smallest opening directly below the item, and becomes zero if
one of the lanes that the item spans has no opening directly below it.
`GetAvailableAlignmentSpaceForItem()` is removed, and the iterator reads
the shared space instead, so the total cost is O(N) in every case.

Grid-lanes gap decorations will reuse this space to find empty openings.
They need the space of every item above an opening, including items that
cannot align.

[PerformanceManager] Update RenderProcessHost priority when exited

ProcessPriorityPolicy is responsible for keeping a renderer's
RenderProcessHost priority in sync with its ProcessNode priority. To
avoid updating a process that has already exited, SetProcessPriority()
skips priority updates while ProcessNode::GetExitStatus() is set.

However, when a RenderProcessHost is reused to launch a new process
(such as when reloading a crashed tab), GetExitStatus() remains set from
the previous process until the new process finishes launching. Any
priority changes during that window, such as raising a crashed tab from
best-effort back to user-blocking on reload, were skipped and never
applied to the new process.

This behavior tested by CrashRecoveryBrowserTest.Reload was hidden by
the MigrateAutomaticJsOptimizer field trial config, because that feature
would change the reloaded page's process lock and force the reload to
create a new RenderProcessHost instead of reusing the crashed one.

Fix this by removing the GetExitStatus() check in SetProcessPriority().
RenderProcessHostImpl already avoids setting priority on exited
processes, so updating the override while exited is safe and ensures the
RenderProcessHost has the current priority if it is relaunched.

Co-authored using Antigravity

FinishRestart() immediately. This removes the restart_id from

CrostiniInstaller::restart_id_ to kUninitializedRestartId and sets

restart already completed synchronously, matching the existing early
return behavior when the uninstaller is running. Also restore the
CHECK_EQ in CrostiniInstaller::OnAvailableDiskSpace().

On Android 14+ (UPSIDE_DOWN_CAKE, API 34+), ActivityManagerService
deprecated and stopped dispatching TRIM_MEMORY_RUNNING_* (5, 10, 15),
TRIM_MEMORY_MODERATE (60), and TRIM_MEMORY_COMPLETE (80) callbacks.

(40) before being frozen by the Cached App Freezer.

true for (level >= TRIM_MEMORY_RUNNING_LOW && level <
TRIM_MEMORY_UI_HIDDEN) || level >= TRIM_MEMORY_MODERATE, which caused

code on Android 14+.

Prevent WebContents destruction while creating the RenderWidgetHostView

WebContentsViewAura::CreateViewForWidget() creates a
RenderWidgetHostViewAura, calls InitAsChild() on it, and then keeps
using the pointer it created. On Windows, InitAsChild() ends in
ui::tsf_inputscope::SetInputScope(), which potentially starts a
synchronous TSF lock session and pumps a nested message loop. Work
running there can tear the tab down: RenderWidgetHostViewAura::Destroy()
deletes the aura::Window, whose destructor deletes the view via
OnWindowDestroyed(), leaving the raw view pointer dangling.

The view being deleted is indicative of the WebContents being destroyed.
If the nested loop tears the tab down, WebContentsViewAura and the
RenderWidgetHost are likely destroyed too. Anything done after
InitAsChild() returns, such as calling GetRenderWidgetHostViewParent()
or passing this to SetDragDropDelegate(), would result in a UAF.

To prevent the UAF, we hold prevent_destruction_ with a
base::AutoReset<bool> for the duration of view creation, so a re-entrant
WebContents destruction fails a CHECK in ~WebContentsImpl. This is the
same mechanism WebContentsImpl::CreateRenderViewForRenderManager()
already uses.

Moving SetInputScope out of InitAsChild() would remove the nested
message loop, but that should be a follow-up change. SetInputScope is
run to mark incognito windows as IS_PRIVATE for TSF. The original change
did this when the view was shown, but that caused regressions, so the
reland moved the code into InitAsChild(). See
https://source.chromium.org/chromium/chromium/src/+/e6b29ca11cf7f1ab7a22b700d6f05162a6b6c46f

CBOR parsers:

   OUT_OF_ORDER_OR_DUPLICATE_KEY error (obsoleting the old histogram
   values so existing buckets are not polluted), checking only whether
   each new key is strictly greater than the immediately preceding key
   rather than binary searching all previously parsed keys.
2. Validate map key type and key ordering before decoding the map value
   instead of decoding the value first and discarding it on key errors.
3. Reject invalid map key types (ARRAY, MAP, SIMPLE_VALUE, and
   INVALID_UTF8 when allow_invalid_utf8 is enabled) directly while
   decoding the map key instead of recursively decoding container keys
   or constructing Value objects only to discard them.

Pre-warm cryptbase.dll on a background thread in NetworkService

On Windows, CryptProtectMemory and CryptUnprotectMemory in crypt32.dll
forward to dpapi.dll, which delay-loads cryptbase.dll. When
CookieOSCryptAsyncDelegate initializes decryption on the Network Service
IO thread during startup, the first call to CryptProtectMemory triggers
dpapi.dll's delay-load of cryptbase.dll synchronously from disk on the
IO thread, accounting for 18.3%-31.3% of active Network IO startup
congestion.

Add a kPrewarmCryptbase feature (enabled by default) that posts a
ThreadPool task during NetworkService construction on Windows to load
and pin cryptbase.dll off the Network IO thread using
base::PinSystemLibrary().

Suppress input to tabs during Android graceful shutdown

With TabAndroidGracefulShutdown, a closed tab's WebContents stays alive
for up to 2s in TabWebContentsDestroyer. In-flight touch/gesture state
was left until final teardown, where queued touch acks are turned into
synthetic gestures while views are being destroyed.

Hold a WebContents::IgnoreInputEvents() token for the destroyer's
lifetime. On Android this resets gesture detection when the tab is
closed, and ignores further input. The token is released before the
WebContents is destroyed.

An already-running fling is not stopped.
